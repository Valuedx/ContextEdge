# Database migrations and reproducibility

## Alembic revision `0001_initial`

The first revision calls `Base.metadata.create_all()` against whatever SQLAlchemy models are importable when **`alembic upgrade head`** runs. It does **not** embed a frozen SQL snapshot in the repository.

**Implications**

- Two greenfield installs at different commits can end up with different `0001` DDL if models changed between those commits.
- **Operational mitigation:** treat `0001` as a bootstrap step, then rely on **`0002+`** (explicit revisions) for every subsequent schema change.
- **Reproducible environments:** after a known-good migrate on a reference commit, capture **`pg_dump --schema-only`** (or restore from a golden image) for CI and staging parity.
- **Downgrade:** `0001` uses `drop_all()` and is destructive; do not use it casually in shared environments.

## Adding schema changes

Always add a new revision (`alembic revision --autogenerate` or hand-written `op.create_table` / `op.add_column`) rather than expecting `0001` to update on existing databases.

See also [Runbook — Database migrations](RUNBOOK.md#database-migrations).

| `0022_contradiction_scan_state` | Adds the `contradiction_scan_state` table, which records one row per `(playbook_version_id, evidence_id)` pair the contradiction scanner has evaluated. | `0023_tenant_llm_budgets` | Adds the `tenant_llm_budgets` table (PK = `tenant_id`, FK-CASCADE to `tenants`) carrying `daily_token_limit` (bigint, nullable), `daily_cost_cap_usd` (numeric(12,4), nullable), `action_on_exceed` (`block` \| `warn`, CHECK-constrained), and `updated_at`. Rows are optional — tenants without a row are uncapped. Enforced pre-call from `ai/provider.llm_complete` via `services/tenant_budget_service.check_budget`, which sums the current UTC day's usage from the existing `llm.usage` operational events (no second source of truth). Either or both axes may be set; whichever is hit first triggers the action. `warn` logs + emits `llm.budget_warning` but lets the call through — useful for rollout tuning before flipping to `block`. Cache of current-day usage is kept per-tenant with a 60s TTL so the enforcement check costs one aggregation query per minute per tenant, not per LLM call. |
| `0024_evidence_scale_indexes` | Adds three indexes on `evidence_items` sized for enterprise-scale row counts without requiring a partition conversion: a BRIN on `(tenant_id, ingested_at)` (~1 KB per million rows; excellent for time-range admin / drift / retention queries), a partial B-tree on `(tenant_id, relevance_state) WHERE relevance_state IN ('relevant', 'unclassified')` for the reviewer-queue hot path, and a partial B-tree on `(tenant_id, updated_at) WHERE relevance_state = 'archived'` for the `purge_archived_evidence` sweep. All three built with `CREATE INDEX CONCURRENTLY` inside `autocommit_block()` — zero table lock. Scoped down from `ENTERPRISE_ARCHITECTURE_REVIEW.md` §6 item 12; the full partition-conversion runbook is deferred to `codewiki/04-evidence-normalization-and-storage.md` under "Partitioning plan (deferred)" because it needs real customer volume numbers to size correctly. |
| `0025_jsonb_gin_indexes` | Adds two GIN indexes on JSONB hot spots flagged in `ENTERPRISE_ARCHITECTURE_REVIEW.md` §5 "Architectural concerns — watch list". `ix_graph_edges_metadata_extra_gin` on `graph_edges.metadata_extra` turns future edge-metadata queries ("find edges where `metadata.reason = X`") from full scans into index hits. `ix_evidence_items_canonical_entity_refs_gin` on `evidence_items.canonical_entity_refs` does the same for identity / decision / correlation filters that hit the JSONB blob. Both use `jsonb_path_ops` — smaller on disk and faster for the `@>` containment operator the existing queries use; add a separate default-ops index if key-exists (`?`) queries land later. Built with `CREATE INDEX CONCURRENTLY` inside `autocommit_block()`. Other JSONB columns (`context_snapshot`, `evidence_summary`, `baseline_ref`, `modification_diff`) stay un-indexed until a real query path justifies the write-amplification cost. |
| `0026_dedup_uniqueness` | Closes two check-then-insert races flagged in the 2026-04 implementation review. Adds `uq_evidence_items_tenant_content_hash` — a **partial** unique index on `(tenant_id, content_hash) WHERE content_hash IS NOT NULL` (review L-02) — so two normalize workers racing on the same raw payload can no longer both insert; the second gets `IntegrityError`, which `_normalize` now catches and resolves by re-fetching the winning row. Adds `uq_contradictions_tenant_source_pair` — a plain unique index on `(tenant_id, source_a_ref, source_b_ref)` (review F-24) — for the same pattern on `_get_or_create_contradiction`. Both indexes built with `CREATE UNIQUE INDEX CONCURRENTLY` inside `autocommit_block()`. **Pre-migration dedupe required** for deployments that accumulated duplicates under the previous race window — see the dedupe SQL in the migration file's module docstring; run before `alembic upgrade` or the `CREATE UNIQUE INDEX` will fail on the existing duplicates. |
| `0027_playbook_evidence_link_fk` | Adds `FK playbook_evidence_links.evidence_id → evidence_items(id) ON DELETE SET NULL` (review F-19). Before this, the column was a plain nullable UUID with no constraint, so a `purge_archived_evidence(mode="hard_delete")` call left dangling pointers in the link table. SET NULL rather than CASCADE is deliberate — the link row records "this playbook version was built with support from evidence that has since been removed", which is a real compliance record we want to preserve. **Pre-migration dedupe required** on deployments that already executed a hard-delete under the old model: `UPDATE playbook_evidence_links SET evidence_id = NULL WHERE evidence_id NOT IN (SELECT id FROM evidence_items)`. Ships alongside new `workers/cleanup_tasks.py::cleanup_hard_deleted_evidence` Beat task (daily) that reaps the other two hard-delete orphan classes — MinIO raw blobs (F-18) and `graph_edges` rows referencing deleted evidence (F-20). |
| `0028_orm_ddl_drift_alignment` | Closes the L-01 ORM-DDL drift: every `ondelete=` / `unique=True` tightening added to the ORM after `0001_initial` (commit `056eb846`, 2026-04-05) was audited against the migration chain. Three FKs diverged — all added in commit `45ad8791` on 2026-04-20 with no corresponding ALTER migration: `attachment_artifacts.evidence_id`, `correlation_edges.source_evidence_id`, `correlation_edges.target_evidence_id`, each `→ evidence_items(id)`. This migration runs `ALTER TABLE DROP CONSTRAINT IF EXISTS` → `ADD CONSTRAINT ... ON DELETE CASCADE` for each. Idempotent on fresh DBs (drop-and-readd of the same CASCADE is a behaviour-equivalent no-op) and safe on older DBs (`IF EXISTS` tolerates hand-renamed constraints). A new CI regression guard (`tests/test_review_orm_ddl_drift.py`) pins the set of in-ORM tightening constraints so a future add that forgets its migration fails at test time rather than silently diverging on older DBs. |
| `0029_ae_ops_concept_alignment` | Aligns the schema with the AE Ops Context Graph design (`ae_ops_context_graph_design.md`). Strictly additive — no rename, no drop, no type change on existing columns. Adds nine new tables: `entities` (operational-noun graph node — workflow / agent_machine / schedule / output_location, coexists with `canonical_identities` which keeps its identity-resolution role), `claims` + `claim_evidence` (evidence-backed assertion with validation lifecycle: unverified → machine_verified → human_validated → rejected → superseded), `decision_evidence` (relational link supplementing the existing `decisions.evidence_summary JSONB` cache for query-by-evidence), `action_policies` (action-keyed policy with `policy_result` verdict — allowed_auto / approval_required / recommendation_only / restricted / manual_only — separate from the generic `tenant_policies` config bucket), `error_signatures` + `fix_patterns` (normalised error fingerprint with success/failure counters and a statistical-fix recommender, separate from `patterns` / `playbooks` which keep their existing semantics), `case_outcomes` + `case_state_transitions` (case-level outcome distinct from per-decision `decision_outcomes`, plus lifecycle history). Adds 32 nullable columns across six existing tables: `resolution_sessions` gets the case spine (case_number partial-unique + case_type / issue_type / priority / severity / environment + four `entities` FKs); `evidence_items` gets evidence_time / collected_by / source_type / redaction_status; `decisions` gets decision_intent / decision_summary / trace-level risk_level / policy_result; `decision_trace_events` gets a `decision_id` FK + tool_name / tool_input_ref / tool_output_ref so rows can serve the cg_decision_step role; `approval_requests` gets action_name / approver_role / approval_channel / recommended_by + executed_by SoD fields / case_id + decision_trace_id FKs; `execution_step_runs` gets action_name / action_type / execution_mode / executed_by / **`idempotency_key` with a partial unique index** (banking-grade duplicate prevention) / case_id + decision_trace_id FKs; `graph_edges` gets `valid_from` / `valid_to` / `confidence` enabling "what was true at incident time?" queries. Idempotent (`IF NOT EXISTS` everywhere, `pg_constraint` lookups guard FK adds) and fully reversible. The ORM-DDL drift snapshot in `tests/test_review_orm_ddl_drift.py` is updated for the new constraints. **No backfill required** — existing rows continue to work because every new column is nullable. **No service code changes** — population of the new fields is the next wave's job. See [codewiki/17-ae-ops-context-graph-alignment.md](../codewiki/17-ae-ops-context-graph-alignment.md) for the narrative. |
| `0030_evidence_chunks` | Closes the historical "8 KB cliff" — `embed_evidence(title, body[:8000])` made any body content past ~8,000 characters invisible to semantic retrieval. Adds the `evidence_chunks` sibling table (FK `evidence_id → evidence_items(id) ON DELETE CASCADE`) with one row per per-source-meaningful unit (Jira description, Teams message, runbook heading section, log event), each carrying a 3072-dim `Vector` embedding, a `chunker_version` for re-chunk safety, and a JSONB `metadata` blob (per-source author / priority / severity / `parent_section` breadcrumb / `source_authority` tag). Adds the GIN index `ix_evidence_chunks_metadata_gin` (`jsonb_path_ops`, matching `0025`). HNSW supports at most 2000 dimensions for the pgvector `vector` type, so the 3072-dimension chunk HNSW index is safely skipped and cosine search remains available as an exact scan. Adds `evidence_items.chunked_at TIMESTAMPTZ NULL` and `evidence_items.chunk_count INT NOT NULL DEFAULT 0`, plus a partial B-tree `ix_evidence_items_chunked_at_null` on `(tenant_id, ingested_at DESC) WHERE chunked_at IS NULL` to drive the future backfill cheaply. Strictly additive: no FK targeting `evidence_items.id` is touched, the parent's `embedding` column is preserved unchanged, contradiction scanning / similar-decision retrieval / baseline matching all keep working without modification. Pairs with new `services/chunkers/`, `services/evidence_chunk_service.py`, `workers/chunk_tasks.py`, and `_dispatch_chunking` wiring inside `workers/extraction_tasks.py::_normalize`. **No backfill required for the schema** — existing `EvidenceItem` rows keep `chunked_at = NULL` until a follow-up backfill task drains them; chunked retrieval co-exists with parent retrieval until the search-side rollup lands. See [codewiki/CHUNKING_DESIGN.md](../codewiki/CHUNKING_DESIGN.md) for the narrative and [codewiki/KNOWN_GAPS.md](../codewiki/KNOWN_GAPS.md) "Resolved: Evidence chunking foundation" for the deferred-follow-up list. |
| `0055_generation_provenance` | Adds `generation_provenance JSONB NULL` to `episodes`, `patterns`, and `playbook_versions` — the three artifacts an LLM *generates* (F5). Prompt name/version and the routed model already reached the `llm.usage` operational event; they never reached the row the call produced, so "which prompt version wrote this episode?" needed a correlation-id join that only worked when the caller happened to hold a `db` session. Generators stamp `{prompt_name, prompt_version, task, model_requested, correlation_id}` via `ai/provenance.generation_provenance`, always *after* the schema gate so the model can neither supply nor influence its own provenance. The field is `model_requested`, not `model`, because E1's circuit breaker can substitute `settings.llm_fallback_model` mid-call and only `llm.usage` observes that — `correlation_id` is the join key to the event that knows the serving model. Deliberately **not** added to `decisions` or `claims`: those rows are written by services and humans, not by a prompt, and a column that is NULL by construction is exactly the schema-claims-capability problem Epic F exists to stop. Nullable with no backfill — a row generated before this has no provenance, and NULL means "unknown", never "the current default". |
| `0056_policy_versioning_and_checks` | Versions the policy that is actually enforced and records every evaluation (F3). Adds `version` (default 1) / `effective_from` / `effective_to` to `tenant_policies`, and a `policy_checks` table: one append-only row per evaluation carrying policy id, **policy version**, check name, evaluated entity type + id, result (`pass` / `fail` / `not_applicable`), reason, input snapshot, evaluator, timestamp. Keyed to the policy VERSION rather than the policy row, so editing a policy cannot rewrite the history of what a past run was judged under; `policy_id` is `ON DELETE SET NULL` because "evaluated against a policy that has since been deleted" is a real audit record. Deliberately does **not** touch `action_policies`: that table has no writer, no CRUD API and no evaluation engine, so versioning it would add three more never-written columns — the action-policy engine and its versioning are one item (F3b), scheduled with the executor. Written from `execution_service` at both real enforcement points: the automation-mode cap in `start_execution` (anchored to the playbook — the run row does not exist yet at gate time) and the decider gate in `decide_approval`, including on the denial path. |
| `0057_knowledge_support` | Adds `evidence_items.knowledge_support JSONB NULL` so retrieval can see whether a procedure has ever actually worked (F4). `knowledge_validation_service` has computed empirical support from playbook→knowledge links and *verified* execution outcomes since Phase 3; `knowledge_retrieval_service` ranked on semantic distance and applicability alone, so a procedure with a documented failure history ranked exactly like one with a success history. Stored rather than recomputed per retrieval — that is several queries per candidate article per playbook generation, the same cost argument that kept applicability lexical until `0051` — and refreshed by the event that changes it: a verification verdict, bounded to the knowledge cited by that playbook version. The ranker multiplies cosine distance by a support factor (proven 0.80, emerging 0.92, unproven 1.00, contested 1.25). NULL means not-yet-computed and ranks exactly like `unproven`: neutral. Silence is not failure — most knowledge is never exercised, and treating "no runs" as a negative signal would demote the whole corpus on day one. |
| `0058_skill_registry` | Adds `skills` and `execution_contracts` (F6, first item of M8). `PlaybookStep.tool_ref` had been a free string since it was introduced — declared in the schema, set by nothing, resolved by nothing — so there was no way to ask what a step would invoke, what happens when it times out, whether running it twice is safe, or whether it can be dry-run. `Skill` carries WHAT can be invoked (interface type, endpoint, I/O JSON Schemas, reversibility, rollback skill, allowed principal roles, side-effect class, status, stable `skill_key` + `version`); `ExecutionContract` carries HOW it must be invoked (idempotency mode, dedup window, timeout, max attempts, retry backoff, cancellation, dry-run, concurrency policy, rate limit, credential scope). Two tables rather than one because a single operational envelope governs many skills and folding it in would make every skill restate the same constants. `skills.execution_contract_id` is `ON DELETE RESTRICT`: deleting the contract a live skill runs under would silently strip its timeout and idempotency guarantees. Side-effect classification reuses the existing `SAFETY_CLASSES` values rather than v6's parallel `sideEffectClassification` vocabulary — the executor and the approval policy already gate on that tuple. Registration invariants live in `services/skill_registry_service.py`: a side-effecting skill needs a contract; a high-side-effect or destructive skill may not register as `NOT_IDEMPOTENT` (v6 invariant 8 at the earliest enforceable point); `DEDUPE_ONLY` needs a window; `max_attempts > 1` needs a replay guarantee. No backfill and nothing newly required — existing steps carry no `tool_ref`, so the binding gate has no existing rows to reject. |
| `0059_approval_artifact_binding` | Binds an approval to the exact artifact it approved (F7). Nothing tied an approval to the thing that later ran: `approval_requests` recorded who approved and when, while the step payload lived in `playbook_versions.steps` as mutable JSONB with no content hash, so v6 invariant 2 (no execution of an artifact different from the approved hash) could not be enforced. Adds `artifact_version` / `artifact_hash` / `policy_snapshot` / `expires_at` to `approval_requests`, and a `BEFORE UPDATE` trigger making a **published** version's `steps` immutable — a hash of a mutable row only proves it has not changed since someone last looked. The hash is an RFC 8785 (JCS) canonicalization of the step *in its version*: key order and whitespace cannot cause a false mismatch (a check that cries wolf gets disabled), and an approval for one playbook cannot satisfy execution of another holding an identical step. Written at `request_approval`, re-checked in `record_tool_invocation` — the last moment before a tool runs — with a violation recorded as an `approval.binding_violated` operational event. `expires_at` (4h) is the answer going stale, distinct from the 72h `approval_expiry_service` window for an unanswered request. Existing approvals keep NULL hashes and are allowed through: retro-blocking approvals granted before the mechanism existed would break running deployments to enforce a rule they had no way to satisfy. Adds the `rfc8785` dependency (pure Python, no transitive deps) rather than hand-rolling canonicalization — ECMAScript number serialization and UTF-16 key ordering are the parts a naive `sort_keys` dump gets wrong. |
| `0060_execution_attempts` | Adds `execution_attempts` and makes the idempotency key live (F8). `ExecutionStepRun` carried one status, so a step that timed out and was retried overwrote its own history and "did this run twice?" was unanswerable from the ledger. And `uq_execution_step_runs_idempotency_key` — shipped in `0029` and described there as "the single most important banking-grade safety control in the alignment" — guarded a column nothing ever wrote: the index was real, the control was inert. One row per try, with `attempt_number` derived from what is already recorded (a caller cannot renumber history, and a retry lands as N+1 without knowing N). The `deduplicated` status is the important one: durable evidence that a replay arrived and was recognised, which is the difference between an idempotency control that works and one nobody can prove worked. `timeout` and `cancelled` are distinct from `failed` because a timeout is an unknown outcome, not a failure, and conflating them tells retry logic the wrong thing. The key itself (`services/idempotency_service.py`) is derived from F7's artifact hash scoped to the case — same case, same step payload, same action — and is hashed rather than concatenated because the unique index is global and a readable key would put tenant ids in a structure other tenants' rows share. Only side-effecting steps get one (suppressing a repeated diagnostic would be a bug wearing a safety control's clothes), and skills whose contract declares `NATIVE` idempotency get none either. A recognised duplicate is skipped, recorded as a `deduplicated` attempt plus an `execution.step_deduplicated` event, and refused again at `record_tool_invocation` so the suppression holds at the call site too. |
