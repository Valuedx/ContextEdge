# Database migrations and reproducibility

## Where the chain stands today (verified 2026-08-20)

- **75 revision files** live in `backend/alembic/versions/`.
- The head is **`0074_operational_situations`** (`down_revision = "0073_migrate_knowledge_episodes_to_cases"`, `backend/alembic/versions/0074_operational_situations.py:56`). It is the only head — the chain is linear.
- One revision id in the chain is **not** numbered: `a4ccd43dcf94_enrich_pattern_data` sits between `0006` and `0007` (`backend/alembic/versions/a4ccd43dcf94_enrich_pattern_data.py:13-14`). Scripts that assume "every revision id starts with four digits" will trip on it.
- **Never quote a head number from a document.** Docs go stale between commits; run `alembic heads` (or `alembic current` against the database) and trust that. This page names `0074` only to describe the state on the date above.

Two runtime guards make "the database is behind the code" a loud failure instead of a silent corruption:

| Guard | What it does | Where |
| --- | --- | --- |
| Worker startup check | On the Celery `worker_ready` signal, `_require_migrations_at_head` resolves the bundled scripts' head, reads `alembic_version.version_num`, and `raise SystemExit` on a definite mismatch — including "no `alembic_version` table at all", which is treated as the *most* definite mismatch rather than as an error. An installed layout with no `alembic/` directory returns silently (there is no head to compare against); a transient DB error logs `worker.migration_check_skipped` and lets the worker start. | `backend/src/contextedge/workers/celery_app.py:83-139` |
| API readiness probe | `GET /ready` runs DB `SELECT 1`, the same migration comparison, and a Redis ping (5s timeout each). Any failure returns **503** with `{"status": "not_ready", "checks": {...}}`. An installed layout with no alembic scripts reports the check as explicitly disabled rather than passing. | `backend/src/contextedge/main.py:89-106, 180-209` |

Why this matters in practice: without the worker guard, a worker started against a stale schema happily consumes the `extraction` queue and corrupts ingestion mid-transaction (the rationale is written into `celery_app.py:87-93`).

## Alembic revision `0001_initial`

The first revision calls `Base.metadata.create_all()` against whatever SQLAlchemy models are importable when **`alembic upgrade head`** runs (`backend/alembic/versions/0001_initial_schema.py:39`; downgrade is `drop_all` at line 47). It does **not** embed a frozen SQL snapshot in the repository.

**Implications**

- Two greenfield installs at different commits can end up with different `0001` DDL if models changed between those commits.
- **Operational mitigation:** treat `0001` as a bootstrap step, then rely on **`0002+`** (explicit revisions) for every subsequent schema change.
- **Reproducible environments:** after a known-good migrate on a reference commit, capture **`pg_dump --schema-only`** (or restore from a golden image) for CI and staging parity.
- **Downgrade:** `0001` uses `drop_all()` and is destructive; do not use it casually in shared environments.
- **Fresh installs hide upgrade bugs.** Because `0001` builds from today's models, a fresh database never walks the historical path — so drift that only bites *upgrading* databases stays invisible in development. Two shipped bugs did exactly that: the `alembic_version` width problem below, and the missing mixin timestamps fixed by `0066_timestamp_column_parity`. Treat "it works on a fresh database" as no evidence at all about upgrades.

## The `alembic_version` column width

Alembic sizes `alembic_version.version_num` once, when it first creates the table, and never revisits it: before Alembic 1.10 that was `VARCHAR(32)`, current Alembic uses `VARCHAR(255)`. **Nine** revision ids in this chain are now longer than 32 characters — `0014_notifications_and_playbook_approval_policy` (47), `0073_migrate_knowledge_episodes_to_cases` and `0072_knowledge_case_and_pattern_evidence` (40 apiece), `0005_playbook_version_semantic_unique` (37), `0033_identity_resolution_hardening` (34), and `0006_increase_embedding_dimension`, `0017_rejection_modification_codes`, `0056_policy_versioning_and_checks`, `0068_case_state_and_source_facets` at 33 apiece. It was seven before the `0072`/`0073` pair landed. Count them yourself rather than trusting this number — it grows every time someone writes a descriptive slug, which is exactly why the fix was to widen the column rather than to rename revisions.

A database whose version table was created by an older Alembic therefore fails **on the stamp, not the DDL**:

```
DataError: value too long for type character varying(32)
[SQL: UPDATE alembic_version SET version_num='0056_policy_versioning_and_checks' ...]
```

The migration's own DDL rolls back with it, so nothing is corrupted — the database is simply stuck, in a way that reads like a broken migration rather than a table that predates it. **Fresh installs never see this**, which is why it went unnoticed: every new database is created by a current Alembic.

`alembic/env.py` widens the column in place before running any migration (idempotent; Postgres widens a varchar without rewriting the table). The widening runs on its **own** bootstrap connection with its own commit (`backend/alembic/env.py:70-72`) — doing it on the migration connection made Alembic see a transaction it did not start, and `alembic upgrade` then reported success while changing nothing. The `ALTER COLUMN ... TYPE VARCHAR(255)` itself only fires when the current width is smaller than the target (`backend/src/contextedge/migration_support.py:38, 43-80`).

Renaming the long revisions was rejected: an id is only meaningful while it matches what a deployed database is stamped with, and shortening one turns "stuck" into `Can't locate revision`. Offline (`--sql`) mode is untouched — it has no connection to alter, so a generated script still assumes the target's column is already wide enough.

## Adding schema changes

Always add a new revision (`alembic revision --autogenerate` or hand-written `op.create_table` / `op.add_column`) rather than expecting `0001` to update on existing databases.

Checklist that comes from bugs this repo actually shipped:

1. **Declare it in both places.** A column added to a model needs a matching `CREATE`/`ALTER` in the chain. `0034`, `0049` and `0066` all exist because a model declared columns no migrated database had — an `UndefinedColumn` on every SELECT of that table, invisible on fresh installs. The guard `backend/tests/test_orm_migration_column_parity.py` now reads the chain as text and fails when a model declares a column no revision creates, so write the statements out literally (a loop over f-strings is invisible to that guard). `0074` repeats its four tables' `created_at`/`updated_at` columns by hand for exactly this reason, and says so in a comment above `upgrade()` (`backend/alembic/versions/0074_operational_situations.py:61-66`): factoring them into a helper is the DRY version that passes review and defeats the guard.
2. **Say so when a pre-migration step is required.** `0026` and `0027` both fail on databases that accumulated duplicates or dangling ids under the older model; the dedupe SQL lives in each migration's module docstring and is repeated in [RUNBOOK — Database migrations](RUNBOOK.md#5-database-migrations).
3. **Build big indexes concurrently.** `0024`, `0025`, `0026`, `0032` and `0035` all use `CREATE INDEX CONCURRENTLY` inside `op.get_context().autocommit_block()` so no table lock is taken.
4. **Fail loud on an unmet environment requirement.** `0032` refuses to run below pgvector 0.7 rather than leaving a database whose every semantic search would 500 at runtime.
5. **A data migration that selects on a marker is only as portable as the marker.** `0073` moves rows chosen by `reviewer_state = 'invalidated' AND generation_provenance->>'invalid_reason' = 'source_not_observational'`, and **no code under `backend/src/contextedge` writes either value** — they were set by a one-off operational script on the affected environment. That is intentional (the revision counts its targets first and returns immediately when there are none), but it means the migration is a **no-op on every fresh install and on any database where the script never ran**, and a reader who assumes otherwise will look for cases that were never created. Say which environment a data migration actually changes, in the revision itself.
6. **Migrate, then delete — never delete without migrating.** Also from `0073`: an invalidated episode that resolves to no knowledge source at all is deliberately left alone rather than removed, because nothing would then represent it. It stays `invalidated` — out of clustering (`pattern.cluster_episodes` selects `reviewer_state == "approved"`) and out of the agent projection (`AGENT_VISIBLE_EPISODE_STATES` is `{"approved", "pending_review"}`, `backend/src/contextedge/graph/agent/hydrators.py:108`) — rather than vanishing from both live tables. The live run left 3 such rows.

See also [Runbook — Database migrations](RUNBOOK.md#5-database-migrations).

Four tables: **`operational_situations`** (one bounded real-world occurrence — type, state, severity, `situation_confidence`, the onset/detected/last-signal/stabilizing/resolved timestamps, primary entity and service, five counters, `fingerprint`, `correlation_version`, `merged_into_situation_id`); **`situation_evidence_memberships`** (why one piece of evidence is considered part of it, carrying `score_breakdown` — the decomposed score, not just a total, because "why was INC1002 associated with SIT44" has to be answerable and an opaque 0.87 does not answer it — plus `source_lineage_group`, so an alert, the ticket it opened and the mail it sent count as one observation rather than three); **`situation_entity_impacts`** (what appears affected *and* what appears healthy: `healthy_control` is a first-class `impact_role` because a healthy control narrows a diagnosis as much as a failure does, and the row carries `signal_observed_at` because "database healthy" is useful at two minutes old and dangerous at eight hours); and **`situation_change_candidates`** (a change that might explain it, `weak_candidate` → `confirmed`, where `correlation_score` is a **ranking and never a probability** and `confirmation_basis` keeps `confirmed` reachable only from governed evidence). Deliberately **not** a renamed `CorrelationEdge` — an edge says two evidence items look related, a situation says many signals describe **one** occurrence — and deliberately not an episode: a situation may exist while nothing is resolved. Two invariants are enforced in the database rather than in a service, because both are the kind of thing a later code path forgets: `ck_change_after_onset_not_causal` (a change after onset cannot be `suspected` / `corroborated` / `confirmed` — but it may still be `remediation` or `rollback`) and `ck_situation_merged_has_target` (a merged situation must name what it merged into, and an unmerged one must not pretend to). `fingerprint` is deliberately **not** unique: it is a lookup and duplicate-suppression key, not identity, since the same service can fail twice in one window for unrelated reasons. Uniqueness lives where retries need it — `(situation_id, evidence_id)`, `(situation_id, entity_id, impact_role)`, `(situation_id, change_evidence_id)`. Seven graph relations are registered alongside in `graph/edge_types.py:141-151`; four are MAF-traversable (`situation_affects`, `suspected_change`, `confirmed_change`, `similar_situation`) and three carry written exclusion reasons (`part_of_situation`, `merged_into`, `recurred_from`). **Schema only — no correlation logic runs yet:** nothing under `backend/src/contextedge` constructs any of these models, so the tables are empty, and on this deployment the inputs are missing anyway (only `zoho_desk` is connected; there are zero change records, zero monitoring alerts, zero CI or service entities, and zero topology edges). |
