# Database migrations and reproducibility

## Alembic revision `0001_initial`

The first revision calls `Base.metadata.create_all()` against whatever SQLAlchemy models are importable when **`alembic upgrade head`** runs. It does **not** embed a frozen SQL snapshot in the repository.

**Implications**

- Two greenfield installs at different commits can end up with different `0001` DDL if models changed between those commits.
- **Operational mitigation:** treat `0001` as a bootstrap step, then rely on **`0002+`** (explicit revisions) for every subsequent schema change.
- **Reproducible environments:** after a known-good migrate on a reference commit, capture **`pg_dump --schema-only`** (or restore from a golden image) for CI and staging parity.
- **Downgrade:** `0001` uses `drop_all()` and is destructive; do not use it casually in shared environments.

## Adding schema changes

Always add a new revision (`alembic revision --autogenerate` or hand-written `op.create_table` / `op.add_column`) rather than expecting `0001` to update on existing databases.

See also [Runbook — Database migrations](RUNBOOK.md#database-migrations).

## Notable revisions

| Revision | Summary |
| --- | --- |
| `0016_first_class_decisions` | Introduces `decisions`, `decision_options`, and `decision_outcomes` tables with graph-edge connectivity. See [codewiki/16-decision-traces.md](../codewiki/16-decision-traces.md). |
| `0017_rejection_modification_codes` | Adds structured code columns to the human-in-the-loop flow: `decision_options.rejection_code`, `decision_outcomes.feedback_code`, and `approval_requests.modification_diff` + `modification_reason_code`. Additive only — existing free-text `rejection_reason` / `decision_comment` fields stay for the `other` + write-in case. Enables the `POST /decisions/{id}/reject` endpoint and the Approve / Modify / Reject learning loop. |
| `0018_playbook_step_metadata` | Adds `playbook_versions.verification_policy JSONB` for the reviewer console's Zone 6 "auto-close on successful recheck" commitment. Paired with the new `PlaybookStep` Pydantic schema (in `schemas/playbook.py`, stored inside the existing `steps` JSONB array), this gives each step reversibility, time estimate, verification flag, rollback hint, safety-class override, and tool reference. Additive only — every new field is optional with sensible defaults, so existing step payloads keep validating. |
| `0019_evidence_baseline` | Adds `evidence_items.baseline_ref JSONB` and `evidence_items.delta_signal VARCHAR(20)` (with a partial index) for the reviewer console's Zone 4 evidence cards that need a current value plus a baseline comparison ("was 74% a week ago", "first observation in 7d window"). The `compute_evidence_baseline` worker (`workers/evidence_baseline_tasks.py`, routed to the `extraction` queue) fans out from normalization and artifact extraction. Additive only — no backfill; existing rows stay null until the next re-ingest or manual recompute. |
| `0020_decision_embedding` | Adds `decisions.embedding Vector(3072)` for semantic similar-decision retrieval. `create_decision` embeds `decision_type + compact_trace + rationale_summary` inline post-flush with graceful fail (provider hiccup leaves embedding null, doesn't fail the write). `find_similar_decisions` accepts `query_decision_id` / `query_text` and orders by `embedding <=> query` cosine distance when a query embedding is available, falling back to the existing `created_at DESC` path otherwise. JSONB containment on `context_snapshot` stays as a structural pre-filter in both paths. **No vector index added in this revision** (matches the existing `evidence_items.embedding` pattern — full-table scan is fine at current scale; an HNSW / IVFFlat index is a follow-up when decision row counts warrant it). |
| `0021_hnsw_vector_indexes` | Adds HNSW indexes with `vector_cosine_ops` on both `evidence_items.embedding` and `decisions.embedding`, closing the follow-up flagged in `0020`. Built with `CREATE INDEX CONCURRENTLY` (no table lock), parameters `m = 16`, `ef_construction = 64` (pgvector defaults — ~95% recall). Runtime recall/latency trade-off is tunable per connection via `SET LOCAL hnsw.ef_search = <n>`. Requires `pgvector >= 0.5.0`; `pyproject.toml` bumped accordingly. On a fresh deployment the build is instant; on a backfilled deployment it may take minutes-to-hours depending on row count, but never blocks queries thanks to `CONCURRENTLY`. |
| `0022_contradiction_scan_state` | Adds the `contradiction_scan_state` table, which records one row per `(playbook_version_id, evidence_id)` pair the contradiction scanner has evaluated. Columns: `last_scanned_at` (timestamptz), `result` (`contradicts` \| `no_contradiction` \| `skipped_token_overlap` \| `skipped_budget` \| `skipped_llm_error`), `skip_reason` (nullable text). Unique constraint on `(playbook_version_id, evidence_id)` lets the scanner upsert its cursor. Partial index on skipped results for queue-depth queries. Cascades via FK to both parent tables so purged evidence or deprecated playbook versions clean up automatically. Powers the incremental-cursor half of the Weeks 3-4 contradiction-scanner redesign: warm tenants skip the embedding + LLM gates on pairs seen inside the rescan-staleness window (default: re-evaluate after 24h or on playbook-version change). |
| `0023_tenant_llm_budgets` | Adds the `tenant_llm_budgets` table (PK = `tenant_id`, FK-CASCADE to `tenants`) carrying `daily_token_limit` (bigint, nullable), `daily_cost_cap_usd` (numeric(12,4), nullable), `action_on_exceed` (`block` \| `warn`, CHECK-constrained), and `updated_at`. Rows are optional — tenants without a row are uncapped. Enforced pre-call from `ai/provider.llm_complete` via `services/tenant_budget_service.check_budget`, which sums the current UTC day's usage from the existing `llm.usage` operational events (no second source of truth). Either or both axes may be set; whichever is hit first triggers the action. `warn` logs + emits `llm.budget_warning` but lets the call through — useful for rollout tuning before flipping to `block`. Cache of current-day usage is kept per-tenant with a 60s TTL so the enforcement check costs one aggregation query per minute per tenant, not per LLM call. |
| `0024_evidence_scale_indexes` | Adds three indexes on `evidence_items` sized for enterprise-scale row counts without requiring a partition conversion: a BRIN on `(tenant_id, ingested_at)` (~1 KB per million rows; excellent for time-range admin / drift / retention queries), a partial B-tree on `(tenant_id, relevance_state) WHERE relevance_state IN ('relevant', 'unclassified')` for the reviewer-queue hot path, and a partial B-tree on `(tenant_id, updated_at) WHERE relevance_state = 'archived'` for the `purge_archived_evidence` sweep. All three built with `CREATE INDEX CONCURRENTLY` inside `autocommit_block()` — zero table lock. Scoped down from `ENTERPRISE_ARCHITECTURE_REVIEW.md` §6 item 12; the full partition-conversion runbook is deferred to `codewiki/04-evidence-normalization-and-storage.md` under "Partitioning plan (deferred)" because it needs real customer volume numbers to size correctly. |
| `0025_jsonb_gin_indexes` | Adds two GIN indexes on JSONB hot spots flagged in `ENTERPRISE_ARCHITECTURE_REVIEW.md` §5 "Architectural concerns — watch list". `ix_graph_edges_metadata_extra_gin` on `graph_edges.metadata_extra` turns future edge-metadata queries ("find edges where `metadata.reason = X`") from full scans into index hits. `ix_evidence_items_canonical_entity_refs_gin` on `evidence_items.canonical_entity_refs` does the same for identity / decision / correlation filters that hit the JSONB blob. Both use `jsonb_path_ops` — smaller on disk and faster for the `@>` containment operator the existing queries use; add a separate default-ops index if key-exists (`?`) queries land later. Built with `CREATE INDEX CONCURRENTLY` inside `autocommit_block()`. Other JSONB columns (`context_snapshot`, `evidence_summary`, `baseline_ref`, `modification_diff`) stay un-indexed until a real query path justifies the write-amplification cost. |
| `0026_dedup_uniqueness` | Closes two check-then-insert races flagged in the 2026-04 implementation review. Adds `uq_evidence_items_tenant_content_hash` — a **partial** unique index on `(tenant_id, content_hash) WHERE content_hash IS NOT NULL` (review L-02) — so two normalize workers racing on the same raw payload can no longer both insert; the second gets `IntegrityError`, which `_normalize` now catches and resolves by re-fetching the winning row. Adds `uq_contradictions_tenant_source_pair` — a plain unique index on `(tenant_id, source_a_ref, source_b_ref)` (review F-24) — for the same pattern on `_get_or_create_contradiction`. Both indexes built with `CREATE UNIQUE INDEX CONCURRENTLY` inside `autocommit_block()`. **Pre-migration dedupe required** for deployments that accumulated duplicates under the previous race window — see the dedupe SQL in the migration file's module docstring; run before `alembic upgrade` or the `CREATE UNIQUE INDEX` will fail on the existing duplicates. |
| `0027_playbook_evidence_link_fk` | Adds `FK playbook_evidence_links.evidence_id → evidence_items(id) ON DELETE SET NULL` (review F-19). Before this, the column was a plain nullable UUID with no constraint, so a `purge_archived_evidence(mode="hard_delete")` call left dangling pointers in the link table. SET NULL rather than CASCADE is deliberate — the link row records "this playbook version was built with support from evidence that has since been removed", which is a real compliance record we want to preserve. **Pre-migration dedupe required** on deployments that already executed a hard-delete under the old model: `UPDATE playbook_evidence_links SET evidence_id = NULL WHERE evidence_id NOT IN (SELECT id FROM evidence_items)`. Ships alongside new `workers/cleanup_tasks.py::cleanup_hard_deleted_evidence` Beat task (daily) that reaps the other two hard-delete orphan classes — MinIO raw blobs (F-18) and `graph_edges` rows referencing deleted evidence (F-20). |
| `0028_orm_ddl_drift_alignment` | Closes the L-01 ORM-DDL drift: every `ondelete=` / `unique=True` tightening added to the ORM after `0001_initial` (commit `056eb846`, 2026-04-05) was audited against the migration chain. Three FKs diverged — all added in commit `45ad8791` on 2026-04-20 with no corresponding ALTER migration: `attachment_artifacts.evidence_id`, `correlation_edges.source_evidence_id`, `correlation_edges.target_evidence_id`, each `→ evidence_items(id)`. This migration runs `ALTER TABLE DROP CONSTRAINT IF EXISTS` → `ADD CONSTRAINT ... ON DELETE CASCADE` for each. Idempotent on fresh DBs (drop-and-readd of the same CASCADE is a behaviour-equivalent no-op) and safe on older DBs (`IF EXISTS` tolerates hand-renamed constraints). A new CI regression guard (`tests/test_review_orm_ddl_drift.py`) pins the set of in-ORM tightening constraints so a future add that forgets its migration fails at test time rather than silently diverging on older DBs. |
