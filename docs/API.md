## Request lifecycle — what happens to every call

Two middleware layers, an auth dependency and a DB session wrap every call before your handler sees it. Knowing the order saves a lot of debugging.

`create_app()` adds middleware in this order: `RequestAuditMiddleware`, `TenantContextMiddleware`, `CORSMiddleware` (`backend/src/contextedge/main.py:122-130`). Starlette wraps the **last-added outermost**, so the effective path is:

```
CORS -> TenantContextMiddleware -> RequestAuditMiddleware -> router -> handler
```

1. **`TenantContextMiddleware`** (`backend/src/contextedge/middleware/request_context.py:74-152`) mints or accepts three ids — `request_id` (header `x-request-id`, else a fresh uuid4), `correlation_id` (`x-correlation-id`, else the request id) and `causation_id` (`x-causation-id`, else the request id) — and binds them into a ContextVar (`request_context.py:88-104`). It also decodes the Bearer JWT, or the `X-Service-Token`, onto `request.state` **without enforcing anything** (`request_context.py:106-134`) — that is for logging and auditing only; the real check is the route dependency. Responses echo `X-Request-ID` and `X-Correlation-ID` (`request_context.py:145-146`).
2. **Auth dependency** `get_current_user` (`backend/src/contextedge/deps.py:72-114`) resolves the principal. `X-Service-Token` wins when present (invalid -> 403); otherwise the Bearer JWT is decoded (invalid or expired -> 401).
3. **DB session** `get_db` (`backend/src/contextedge/database.py:29-42`) hands the handler one `AsyncSession` from a pooled engine (`pool_size=20, max_overflow=10`, `database.py:19-21`) and commits it at the end if the session is still active. Handlers therefore `flush()` and let the dependency commit — an explicit `await db.commit()` in a handler is deliberate (see the episode-approve ordering note below), not the norm.
4. **`RequestAuditMiddleware`** (`backend/src/contextedge/middleware/request_audit.py:25-124`) runs *after* the response for every `POST/PATCH/PUT/DELETE` under `/api/v1` except `/auth/login`. It always writes a structlog `http.mutating_request` line, and additionally inserts an `audit_logs` row when a tenant resolved. The insert uses a separate **sync** engine off-thread and swallows its own errors (`audit_db_error`) — auditing must never turn a successful request into a failed one (`request_audit.py:89-119`). Unauthenticated 401 probes never resolve a tenant, so they exist only in the log line, not the table (`request_audit.py:59-64`).
5. **Unhandled exceptions** are caught by a global handler that logs the full detail server-side and returns only `{"detail": "Internal server error", "request_id": ...}`. It re-adds CORS headers by hand, because it runs outside `CORSMiddleware` and without them a browser could never read the very `request_id` it exists to hand back (`main.py:132-166`).

### The ids follow the work into the workers

Any endpoint that calls `task.delay(...)` hands its ids to Celery automatically. The `before_task_publish` signal `_inject_correlation_headers` copies `request_id` / `correlation_id` / `causation_id` from the ContextVar into the task message headers using `setdefault`, so a caller-set header is never clobbered (`backend/src/contextedge/workers/celery_app.py:25-42`). On the worker, `task_prerun` re-binds them for the task's lifetime and `task_postrun` releases them (`celery_app.py:45-80`). Anything the task then writes through `append_operational_event` inherits the same ids (`backend/src/contextedge/services/event_log_service.py:54-56`).

Practical payoff: an operator clicks "retry sync" for Acme's ServiceNow source, and the `llm.usage` events for classifying `INC0010427`'s evidence carry the same `correlation_id` as that click. One id joins the button to the spend.

### Which queue a dispatch lands on

Most endpoints that return `TaskDispatchResponse` are enqueueing, not doing (the exception is called out below). Routing is order-matched in `task_routes` (`backend/src/contextedge/workers/celery_app.py:226-279`):

| Endpoint | Task | Queue |
| --- | --- | --- |
| `POST /sources/{id}/backfill` | `sync.run_backfill` | `sync` |
| `POST /sync-runs/{id}/retry` | `sync.run_backfill` or `sync.run_incremental_sync` | `sync` |
| `POST /threads/{id}/hydrate` | `hydration.hydrate_thread` | `hydration` |
| `POST /episodes/reconstruct` | `extraction.reconstruct_episode` | `correlation` |
| `POST /episodes/ai-review` | `evaluation.ai_review_episodes` | `evaluation` |
| `POST /patterns/cluster` | `pattern.cluster_episodes` | `pattern` |
| (ingest fan-out) | `extraction.chunk_evidence`, `extraction.embed_chunks_batch` | `embedding` |
| (ingest fan-out) | `extraction.correlate_evidence`, `extraction.compute_evidence_baseline` | `correlation` |

Not everything that looks asynchronous is. `POST /patterns/discover` and `POST /patterns/deduplicate` run inline in the request, LLM calls and all; `POST /sources/{id}/discover` runs discovery inline; and `POST /sources/local-ingest` returns the `TaskDispatchResponse` shape but does the work in the request too — see the note under "Shared response shapes".

The full consumed set is **eight** queues — `default, sync, hydration, extraction, correlation, embedding, pattern, evaluation` (`backend/dev.py:16`). `correlation` and `embedding` were split out on 2026-08-17 because the graph and retrieval stages were starving behind bulk normalization in one FIFO lane (`celery_app.py:234-268`). A worker fleet that does not consume all eight will accept your dispatch and silently never run it.

## Authentication

### Human users (JWT)

1. `POST /api/v1/auth/login` with `{"email", "password"}`
2. Receive `{access_token, expires_in}` — `expires_in` is in **seconds**, computed as `JWT_ACCESS_TOKEN_EXPIRE_MINUTES x 60`, so the default 60-minute setting comes back as `3600` (`backend/src/contextedge/api/v1/auth.py:98-101`)
3. Send `Authorization: Bearer <access_token>` on subsequent requests

**Claims the login endpoint mints** (`auth.py:21-32`): `sub`, `tenant_id`, `email`, `roles`, `exp`. Nothing else.

**Claims the API will read if an external issuer supplies them** (`backend/src/contextedge/deps.py:97-108`): `workspace_ids` and `allowed_domain_ids`, both optional lists of UUIDs. The built-in login never sets either, so on a stock deployment `CurrentUser.workspace_ids` is `[]` and `allowed_domain_ids` is `None`. Do not assume a login-issued token carries workspace scope.

Three login behaviours worth knowing, because they look like bugs otherwise (`auth.py:35-101`):

- `User.email` is unique **per tenant**, not globally. Login fetches up to 5 active matches rather than one — a duplicate address across tenants would otherwise 500 (`auth.py:43-49`). Hitting the cap logs `auth.candidate_cap_reached`.
- Same email *and* same password in two tenants returns **401 "Ambiguous account"** rather than guessing which tenant you meant (`auth.py:76-89`).
- An unknown email still runs one bcrypt verify against a throwaway hash, so response time cannot be used to enumerate accounts (`auth.py:16-18, 58-64`). All bcrypt work runs on a thread, never the event loop (`auth.py:66-73`).

### Service accounts and integrations

- Header: `X-Service-Token: <opaque-token>`
- Tokens are defined in `SERVICE_TOKENS_JSON` — a JSON map of token -> `{tenant_id, user_id, email, roles[, allowed_domain_ids]}` (`backend/src/contextedge/security_tokens.py:12-36`)
- Resolved into a `CurrentUser` with `principal_type="service_account"` (`deps.py:54-69`)
- A service token that is present but not valid is **403, not 401** — the caller identified itself and was refused (`deps.py:76-83`)

Runtime-specific behavior:

- If `allowed_domain_ids` is set, `/runtime/match` and `/runtime/playbooks/{stable_key}` are limited to those domains plus tenant-wide playbooks
- If `allowed_domain_ids` is omitted, the token gets full-tenant runtime access
- If `allowed_domain_ids` is `[]`, the token is limited to tenant-wide playbooks only

Implementation paths:

- `contextedge.security_tokens.service_token_context`
- `contextedge.deps.get_current_user`

### Request context middleware

`TenantContextMiddleware` decodes the same Bearer JWT or service token into `request.state` for auditing and logging. It does **not** authorize — a request with a forged token still reaches the route dependency, which is where it is rejected.

Paths skipped by that middleware (`backend/src/contextedge/middleware/request_context.py:77-85`):

- prefix match: `/health`, `/ready`, `/docs`, `/redoc`, `/openapi.json`, `/metrics`
- exact match: `/api/v1/auth/login`

### RBAC

`CurrentUser.has_role(role)` returns `True` unconditionally when the caller holds **any** of `platform_super_admin`, `tenant_admin`, or `admin` — all three are super-roles, not just the first (`backend/src/contextedge/deps.py:37-44`). `require_role(role)` raises 403 when `has_role` says no (`deps.py:46-51`), and is available both as a method and as a dependency factory (`deps.py:117-124`). Routes use one or the other; a handful check roles inline instead (for example `GET /policies`, which accepts tenant_admin, domain_admin or knowledge_manager — `backend/src/contextedge/api/v1/policies.py:59-67`).

Roughly 106 route-level `require_role(...)` calls exist across `api/v1/*.py`, dominated by `knowledge_manager` (49), `tenant_admin` (30) and `domain_admin` (24).

**Load-bearing caveat — role scope is not enforced.** `RoleBinding.scope_type` / `scope_id` are stored (`backend/src/contextedge/models/tenant.py:88-108`) but nothing reads them: login selects role *names* only (`auth.py:92-95`) and `has_role` is a pure name check. A domain admin bound to one domain therefore holds `domain_admin` **tenant-wide** on every `require_role` route. The only finer scoping that actually applies comes from token claims — `allowed_domain_ids` and `workspace_ids` — and only on the routes that consult them. Single-domain tenants are unaffected; multi-domain tenants must treat every role grant as tenant-wide. This is deliberate: a half-honoured scoping change is worse than a documented gap (`codewiki/KNOWN_GAPS.md:187-191`).

Related asymmetry: the frontend's `hasRole` treats only `platform_super_admin` as a super-role (`frontend/src/lib/roles.ts:7-9`) while the backend also short-circuits `tenant_admin` and `admin`. A tenant_admin may not *see* a nav item the API would happily authorize. Nav visibility is UX filtering, never security.

### SSO and enterprise IdP

OIDC and SAML helpers remain in `middleware/auth.py`, but normal development still uses login-issued JWTs or seeded users rather than full per-tenant SSO.

## Sync — dispatch, single-flight, and cooperative control

Everything here is asynchronous: the HTTP call enqueues a Celery task on the `sync` queue and returns. The work happens in `services/sync_worker_service.py`.

### Dispatch endpoints

| Endpoint | Role | What it enqueues |
| --- | --- | --- |
| `POST /sources/{source_id}/discover` | `domain_admin` | Runs discovery inline (no task) and returns the discovered `SourceObject` rows (`backend/src/contextedge/api/v1/sources.py:204-216`) |
| `PATCH /sources/{source_id}/objects/{object_id}` | `tenant_admin` | Approval flags. Setting `approved_for_sync: true` immediately dispatches `sync.run_incremental_sync` (`backend/src/contextedge/api/v1/sources.py:280-282`) |
| `POST /sources/{source_id}/backfill` | `domain_admin` | `sync.run_backfill` (`max_retries=3`, 120s delay) (`sources.py:392`) |
| `POST /sync-runs/{run_id}/retry` | `domain_admin` | `sync.run_backfill` or `sync.run_incremental_sync`, matching the original run type (`backend/src/contextedge/api/v1/sync.py:43-62`) |
| `POST /sources/{source_id}/sync/control` | `domain_admin` | Nothing — it writes a signal the running job reads (below) |

Beat also fans out on its own: `sync.trigger_scheduled_syncs` runs every 15 minutes and dispatches one `run_incremental_sync` per `SourceObject` with `approved_for_sync IS TRUE` (`backend/src/contextedge/workers/sync_tasks.py:16-32`). Backfill additionally requires `approved_for_backfill` and returns `source_object_not_approved_for_backfill` without it (`sync_worker_service.py:445-446`).

### Single-flight is enforced (this changed)

Earlier revisions of this document said the system "does not yet serialize overlapping manual requests for the same `SourceObject`". **It does now.** Both job entry points take a transaction-scoped Postgres advisory lock before touching anything:

```sql
SELECT pg_try_advisory_xact_lock(hashtext('sync:<source_object_id>'))
```

(`backend/src/contextedge/services/sync_worker_service.py:379-395`). A second worker that loses the race returns `{"status": "skipped_locked"}` and logs `sync.skipped_locked` instead of interleaving checkpoint writes (`sync_worker_service.py:427-433` for backfill, `:532` for incremental). Because the lock is transaction-scoped it releases at commit or rollback, so a crashed worker cannot leak it.

Two concurrent backfills for the same object are therefore safe — but the second one does nothing, so treat `skipped_locked` as "already running", not as an error.

### Pause, resume, cancel

`POST /api/v1/sources/{source_id}/sync/control` with `{"action": "pause" | "resume" | "cancel", "source_object_id": "<optional>"}`, gated to `domain_admin` (`backend/src/contextedge/api/v1/sources.py:295-312`). Omit `source_object_id` to act on every object under the source.

Nothing is killed. A backfill holds a page of records in memory that it has already paid the vendor API for, and terminating the worker throws them away. The stop is cooperative:

1. The endpoint sets `SourceObject.metadata_extra["sync_paused"]` and, when a run is active, calls `signal_run` to write `sync_runs.control` (`sources.py:329-352`; `backend/src/contextedge/services/sync_control_service.py:64-95`). Valid signals are `pause` and `cancel`, mapping to terminal statuses `paused` and `cancelled` (`sync_control_service.py:41-43`).
2. The running job installed a callback at start — `connector.set_control_check(control_check_for(...))` (`sync_worker_service.py:476`) — and the connector polls it once per page and every 25 detail records.
3. The check reads `sync_runs.control` on a **fresh connection**, because the job's own transaction opened before the operator pressed anything and cannot see the write (`sync_worker_service.py:398-416`). It never raises: a failing control channel must not kill a healthy sync (`sync_control_service.py:104-119`).
4. Both stops persist what was already fetched **and** the checkpoint. Cancel is not a rollback (`sync_control_service.py:15-24`).
5. `resume` only clears the gate. The paused run has already ended; the next run picks up from the checkpoint (`sources.py:331-337`).
6. Every action is audited as `sync.<action>` (`sources.py:354-363`).

Escape hatch for a worker wedged past answering the check: `sync_runs.celery_task_id` is recorded at run start so it can be revoked by id (`sync_worker_service.py:453-456`). Columns and the `ix_sync_runs_active` partial index come from migration `0069_sync_run_control`.

### What a sync sets in motion

Each fetched record is persisted as a `RawEvidenceObject`, then `extraction.normalize_evidence` runs. **Payloads larger than 32,768 bytes are written to MinIO and the DB row keeps only a stub** — `{"_offloaded": true, "size_bytes": N}` (`backend/src/contextedge/services/ingestion_persistence.py:16, 85-87`). This matters to anyone writing SQL: a filter over `raw_evidence_objects.raw_payload` silently skips the biggest records, which are usually the interesting ones. Readers that need the real payload go through `load_raw_payload`.

After normalization commits, the fan-out is dispatched by the `normalize_evidence` task wrapper — not by `_normalize` itself (`backend/src/contextedge/workers/extraction_tasks.py:1326-1364`):

```
extraction.normalize_evidence            (queue: extraction)
  - relevance classification runs INLINE, before the expensive fan-out
  - parent embedding written inline
  - small bodies chunked inline; everything else -> extraction.chunk_evidence
  |
  +-> extraction.correlate_evidence            (queue: correlation)
  |     +-> extraction.reconstruct_episode     (queue: correlation, countdown 180s)
  +-> extraction.compute_evidence_baseline     (queue: correlation)
  +-> extraction.chunk_evidence / embed_chunks_batch (queue: embedding)
  +-> hydration.hydrate_thread                 (queue: hydration, first time a ticket/email is seen)
```

"Small" means two conditions together, not one: the post-redaction body is under `INLINE_CHUNK_BUDGET_BYTES` (16 KB) **and** the source type is in `INLINE_CHUNK_SOURCE_ALLOWLIST` — currently `jira_sm`, `servicenow`, `gmail`, `teams`, `sapphireims`, `zoho_desk` (`extraction_tasks.py:49-62, 99-119`). A source outside the allowlist always chunks asynchronously, however short its bodies, so an unfamiliar parser can never stall ingest.

If the record carried attachments, `artifact.extract_attachment` runs *instead* of the correlate/baseline pair, and re-dispatches `classify_relevance`, `correlate_evidence` and `compute_evidence_baseline` once extraction finishes (`extraction_tasks.py:1331-1335`; `backend/src/contextedge/workers/artifact_tasks.py:41-43`). On the normal path `extraction.classify_relevance` is **not** dispatched — classification already ran inline — but the task stays registered for manual re-classification from the admin UI (`extraction_tasks.py:1341-1345`).

Because the fan-out lives in the task wrapper, the one caller that invokes `_normalize` directly gets a shorter pipeline: `POST /sources/local-ingest` normalizes, chunks and classifies inline, and never dispatches `correlate_evidence`, `compute_evidence_baseline` or `hydrate_thread` (`backend/src/contextedge/api/v1/sources.py:530-545`). Locally ingested files are searchable but do not join the correlation graph on their own.

## Runtime

Base path: `/api/v1/runtime`.

Implementation: `contextedge.api.v1.runtime`.

### Endpoints

| Method | Path | Description | Handler |
| --- | --- | --- | --- |
| `POST` | `/match` | Builds query text from symptoms, entities, and optional context; hybrid-ranks approved playbooks; returns `match_id`, `results`, `filters_applied`, and optional `fallback_guidance` | `runtime.py:89-246` |
| `GET` | `/explain/{match_id}` | Returns cached scoring and context for the same tenant | `runtime.py:249-267` |
| `GET` | `/playbooks/{stable_key}` | Returns a published playbook version only | `runtime.py:270-349` |
| `POST` | `/feedback` | Records `RetrievalFeedback` | `runtime.py:352-369` |
| `GET` | `/feedback` | Lists recorded feedback, filterable by playbook / type / `match_id` | `runtime.py:372-391` |

### What `POST /match` actually does, in order

1. **Domain validation** — a `domain_id` from another tenant is a 400; a domain outside a service token's `allowed_domain_ids` is a 403 (`runtime.py:76-105`).
2. **Memory assembly** — `build_runtime_memory_context` composes three memory classes and the query text (`backend/src/contextedge/services/memory_service.py:82-288`): *short_term* is a summary of the session row plus the most recently ingested tenant evidence (`memory_service.py:242-246`); *long_term* is the resolved canonical identities plus approved-playbook and active-pattern counts (`:247-259`); *reasoning* is the session's last 5 decision-trace events, its last 3 execution runs and its last 5 decisions (`:260-282`). Trace events live in *reasoning*, not *short_term* — an earlier revision of this document put them in the wrong class. `query_text` is a deduped join of the request's symptoms/entities/context, the session's own symptoms/entities/notes, and the resolved identity names (`memory_service.py:230-240`).
3. **Risk cap** — derived from the caller, see below.
4. **Ranking** — `rank_playbooks(...)` (`runtime.py:130-140`).
5. **Abstention** — if every candidate scores below `MIN_RECOMMENDATION_SCORE = 0.35`, the result list is **empty on purpose** and `ranking.abstained` is logged with the top score (`backend/src/contextedge/search/hybrid_ranker.py:168-171, 368-379`). An empty `results` array means "no recommendation", not "nothing matched the filters".
6. **Fallback guidance** is attached when there are no results or the top confidence is under 0.3 (`runtime.py:162-164`).
7. **Session trail** — when `session_id` is supplied, a `decision_trace_events` row is appended via `append_trace_event(event_type="retrieve", ...)` plus an operational event `decision_trace.retrieve`; an unknown session is a 404 (`runtime.py:166-194`).
8. **Operational event** `runtime.match_completed` records the filters applied and the top result (`runtime.py:196-215`).
9. **Explain cache write** (`runtime.py:230-238`).

### Match explain cache

- Cached in Redis under `runtime:match:{match_id}`
- TTL is `MATCH_CACHE_TTL_SEC = 3600` — one hour (`runtime.py:29`)
- Cache **write** failures are swallowed: a Redis outage degrades explain, never the match itself (`runtime.py:230-238`)
- `/runtime/explain/{match_id}` returns `404` if the cache entry is gone
- `/runtime/explain/{match_id}` returns `403` if the cached payload belongs to another tenant (`runtime.py:249-267`)

### Risk tier cap

Effective maximum risk tier is derived from caller role and principal type, not from `TenantPolicy.config`.

| Caller | Effective cap |
| --- | --- |
| `platform_super_admin`, `tenant_admin`, `domain_admin` | No cap |
| `knowledge_manager`, `service_account` | `high` |
| Other roles | `medium` |

Tier ordering:

`minimal(0) < low(1) < medium(2) < high(3) < critical(4)`

An unrecognised or missing tier is treated as `medium`, not as "allow" (`backend/src/contextedge/search/risk_policy.py:3-13`). `risk_within_cap(tier, None)` allows everything — `None` is the uncapped admin case (`risk_policy.py:16-20`).

Implementation paths:

- `contextedge.search.risk_policy` — the ordering
- `_effective_max_risk_tier` (`backend/src/contextedge/api/v1/runtime.py:42-52`) — the caller-to-cap mapping

### Domain scoping

For `POST /runtime/match`:

- `domain_id` is optional
- If supplied, it must belong to the caller's tenant
- If a service token has `allowed_domain_ids`, the requested domain must be in that allowlist

For `GET /runtime/playbooks/{stable_key}`:

- `domain_id` is optional
- If the playbook is domain-bound, it must match the requested domain
- Tenant-wide playbooks remain accessible when a domain filter is provided
- Service-token allowlists are enforced here as well

### Published version behavior

- Runtime only returns published versions where `published_at` is set
- If `current_version_id` points to an unpublished version, runtime falls back to the latest published version
- Explicit `version=<semantic_version>` also requires that version to be published

### Hybrid ranking summary

`contextedge.search.hybrid_ranker.rank_playbooks(...)` (`backend/src/contextedge/search/hybrid_ranker.py:213-379`) scores every approved playbook with a published version and returns the survivors above the abstention floor.

Weights (`RankingWeights`, `hybrid_ranker.py:22-31`):

| Signal | Weight | Where it comes from |
| --- | --- | --- |
| keyword | 0.25 | `search_playbooks_fts` over `playbooks.search_tsvector`, ranks normalized to `[0,1]` |
| semantic | 0.30 | `search_evidence_semantic_for_playbook` over that version's linked evidence |
| graph_distance | 0.15 | `graph_edges` touching the playbook + `correlation_edges` between its evidence and this query's semantic hits |
| evidence_quality | 0.10 | `0.6 x playbook confidence + 0.4 x min(evidence_hits/5, 1)` |
| identity | 0.05 | distinct `references_identity` edges to the query's resolved identity ids |
| recency | 0.10 | same value as freshness (`hybrid_ranker.py:334`) |
| freshness | 0.05 | 0.0 past `expiry_at`; else `max(0, 1 - days_since_last_validated/180)`; 0.5 when never validated |
| negative_penalty | -0.05 | subtracted — `contradicts` edges plus negative-knowledge entries in the domain |

Because recency mirrors freshness, freshness effectively carries 0.15 of the total.

Two behaviours that surprise people:

- The semantic score is **gated by keyword**: `min(1.0, semantic x (0.6 + 0.4 x keyword_score))` (`hybrid_ranker.py:330`). A playbook with strong vector similarity and zero lexical overlap is deliberately held back.
- Exactly **one** query embedding is generated per match, attributed to the tenant and budget-gated; if it fails, the semantic signal contributes 0 and ranking continues on the other five (`hybrid_ranker.py:271-281`).

Each result carries the full `scoring_breakdown` dict (`hybrid_ranker.py:349-366`), which is what `/runtime/explain/{match_id}` replays.

### Vector search under the hood

Every cosine ordering in the product — evidence search, playbook-scoped search, similar decisions, agent-graph seeds — goes through `halfvec_cosine_distance(column, embedding)` (`backend/src/contextedge/search/vector_ops.py:40-45`).

The reason is worth knowing before you write a query. pgvector's HNSW index on the plain `vector` type caps at 2,000 dimensions and this app stores 3,072, so migrations `0021`/`0030` documented invalid indexes and dropped them. Migration `0032` instead builds HNSW **expression** indexes over `(embedding::halfvec(3072))` on `evidence_items`, `evidence_chunks`, `decisions` and `episodes` (`vector_ops.py:1-15`). The planner only uses those indexes when the query orders by the *same expression* — so a raw `column.cosine_distance(...)` is a guaranteed sequential scan, not a slightly slower one.

Callers also run `await tune_ann_recall(db)` first, which issues `SET LOCAL hnsw.ef_search = 200` for the transaction (`vector_ops.py:31-37`). The indexes are global across tenants while every query post-filters by `tenant_id`; at the default `ef_search=40` a small tenant's rows can be entirely absent from the candidate set and the query quietly returns fewer rows than the limit.

Deployment caveat: `0032` fails loudly below pgvector 0.7, but an environment already stamped at an earlier revision of that file never re-executes it and stays on sequential scans. `docker-compose.yml` pins `pgvector/pgvector:pg16` (`codewiki/KNOWN_GAPS.md:40`).

- Attaching a policy to another resource goes through `/policy-assignments`, which validates type **and** tenant via `assert_policy_assignment` and 400s on a mismatch (`backend/src/contextedge/services/policy_assignment.py:12-35`)

### Versioning rule — read this before writing a PATCH client

`TenantPolicy.version` increments **only when `config` changes**. Renaming a policy or flipping `is_active` does not bump it (`policies.py:133-140`):

```python
if body.config != row.config:
    row.version = (row.version or 1) + 1
row.config = body.config
```

The version tracks the *rules*, not the row. Every `policy_checks` entry is keyed to the version it was judged under, and those rows have to keep meaning what they meant — a rename must not invalidate a past verdict.

### Policy checks — the audit trail

`PolicyCheck` is append-only: one row per evaluation of one policy **version** against one artifact, with `result` in `('pass', 'fail', 'not_applicable')` (`backend/src/contextedge/models/policy.py:26-28, 70-128`). Three values because each maps to a distinct executor action — a policy that merely warns has already allowed. `input_snapshot` records what the check saw, so the verdict stays reproducible; `policy_id` is `ON DELETE SET NULL` because the orphaned row is still a real audit record.

The writer, `record_policy_check` (`backend/src/contextedge/services/policy_check_service.py:34`), is **fail-soft by design**: the gate has already decided, and an audit write must never turn an allowed action into a failed request.

Approval-policy config keys the execution service enforces (`backend/src/contextedge/services/approval_policy_service.py:12-19`): `approver_roles`, `forbid_self_approval`, `require_approval_min_safety_class`, `max_automation_mode`. They are evaluated at `start_execution` and `decide_approval`, and both allow and deny are recorded. Separation of duties is enforced initiator-vs-approver only, never recommender-vs-approver (`codewiki/KNOWN_GAPS.md:12`).

### Current usage

- Sources may reference `classification_policy_id` and `retention_policy_id`
- Evidence items may reference `access_policy_id` — and this one is load-bearing for search: `resolve_excluded_access_policy_ids` collects active `access` policies whose `config.restricted is True` and excludes their evidence from every search surface for non-admin callers (`backend/src/contextedge/search/access_control.py:12-39`)
- Retention policies feed the daily archive sweep: the newest active `retention` policy's `config.retention_days` wins, otherwise `RETENTION_DEFAULT_DAYS` (365) (`backend/src/contextedge/workers/retention_tasks.py:38-65`)
- Runtime risk caps are still role-based today, **not** read from `TenantPolicy.config`
- `/action-policies` is a separate table and engine, not a `TenantPolicy` type

**Open scope inconsistency (P1-6, do not gloss over it):** `POST /agent-subsets` builds a fully scoped projection — tenant, domain, workspace, risk cap, access policies, legal hold. The other graph routes (`/neighbors`, `/subgraph`, `/stats`, `/cmdb-topology`, `/change-risk`, `/fix-applicability`) filter by `tenant_id` only. A domain-limited principal can therefore read wider through those than its own agent projection would allow (`codewiki/KNOWN_GAPS.md:56`). Treat them as tenant-scoped reads until that is closed.

Related: `fix_patterns` has no constructor anywhere in the codebase, so `/fix-applicability` and `/fix-outcomes` operate on a table nothing populates yet — the surface exists, the rows do not (`codewiki/KNOWN_GAPS.md:10`).

Edge proposals come from the MAF `propose_dependency` tool as
`proposed_depends_on` edges — excluded from the maf.v1 projection, so
agents never consume unreviewed topology. Either review verdict closes
the proposal edge (`valid_to`, never deleted); approval records which
proposal, whose review, and the agent's rationale/evidence on the
authored edge's metadata.

The three traversal reads — `/neighbors`, `/subgraph/{type}/{id}` and `/stats` — accept optional `domain_id` and timezone-aware `as_of` parameters. Without `as_of`, only active edges (`valid_to IS NULL`) are returned. Point-in-time reads apply `valid_from <= as_of < valid_to` (`backend/src/contextedge/graph/temporal.py:29-36`).

`normalize_graph_as_of` rejects a naive datetime with a 422 and refuses anything more than five minutes in the future (`temporal.py:12-26`).

**`as_of` semantics caveat:** historical *edges* are combined with **current** node facts. The agent projection says so in an explicit warning; these raw routes do not. Do not draw historical operational conclusions from an `as_of` read (`codewiki/KNOWN_GAPS.md:66`).

Bounds: BFS depth is capped at `MAX_TRAVERSAL_DEPTH = 3`, and subgraph payloads at `MAX_SUBGRAPH_NODES = 250` / `MAX_SUBGRAPH_EDGES = 500` (`backend/src/contextedge/graph/queries.py:12-17`). `/neighbors` has **no per-hop edge cap**, so a hub node at depth 3 can return a lot.

Implementation: `contextedge.api.v1.evidence`, `contextedge.schemas.evidence`, `contextedge.services.evidence_baseline_service`, `contextedge.workers.evidence_baseline_tasks`.

Every `EvidenceItem` carries two optional fields that power the reviewer console's Zone 4 evidence cards — current value + delta comparison + color-coded severity:

| Field | Type | Purpose |
| --- | --- | --- |
| `baseline_ref` | JSONB | Shape is open-ended. ### Baseline computation

After normalization (and after attachment artifact extraction when applicable), `compute_evidence_baseline_task` — task name `extraction.compute_evidence_baseline` (`backend/src/contextedge/workers/evidence_baseline_tasks.py:22-28`) — fans out alongside `correlate_evidence`.

**Queue correction:** both now run on the **`correlation`** queue, not `extraction` (`backend/src/contextedge/workers/celery_app.py:256-258`). They were moved on 2026-08-17 because per-evidence follow-up work was queueing behind the bulk normalization that produces it. If your worker fleet does not consume `correlation`, baselines are dispatched and never computed — and nothing reports an error.

It runs a **relationship-only baseline**: finds the most recent prior `EvidenceItem` in the same tenant + `evidence_type` + `source_object_id` within a 7-day window, records "last seen N days ago" or "first observation in 7d window" into `baseline_ref`, and stamps `delta_signal = "neutral"` if not already set. `max_retries=2`, 60s delay; a failure logs `evidence.baseline_failed` and never blocks the rest of the fan-out.

Skip conditions:

- Evidence has no `source_object_id` — the generic worker needs a stable dedup key; connectors can still populate `baseline_ref` directly at ingest.
- Cross-tenant access — refused for defense-in-depth.
- A connector already stamped `delta_signal` (`amber` / `red`) — the generic worker does **not** overwrite a richer signal.

### What's exposed today vs. deferred

**Corrected 2026-08-19 — the search-side rollup shipped.** `search_evidence_semantic` is now chunk-aware end to end (`backend/src/contextedge/search/vector_search.py:1-15, 204-243`):

1. Embed the query once, then `tune_ann_recall(db)` (`SET LOCAL hnsw.ef_search = 200`).
2. **Chunk pass** — one ANN query over `evidence_chunks` joined to `evidence_items`, ordered by halfvec cosine distance, oversampled to `min(max(80, limit*3), 240)` rows. It selects the chunk id, distance, raw embedding, `parent_section`, `chunk_kind` and a 240-character snippet (`vector_search.py:40-46, 73-158`).
3. **MMR diversification** — greedy maximal marginal relevance, `score = 0.7 x relevance - 0.3 x max_similarity_to_already_selected` (`backend/src/contextedge/search/chunk_rollup.py:31, 79-108`). MMR decides which candidates survive; the rollup's re-sort by distance decides the final order.
4. **Rollup** — one candidate per `evidence_id` (its closest chunk), tie-broken by chunk id for determinism (`chunk_rollup.py:111-121`).
5. **Parent-pass merge** — a second ANN query over `evidence_items.embedding` in the same distance space, appended for parents not already seen (`vector_search.py:161-201`). This is why evidence with no chunks at all — pre-chunking rows, chunker failures — still surfaces.

Results are 3-tuples `(EvidenceItem, distance, best_chunk | None)`, so older consumers that index `row[1]` keep working while new ones can render the matching passage. A corrupt or dimension-mismatched chunk embedding makes MMR degrade to pure distance ordering rather than failing the search (`chunk_rollup.py:59-76`).

**Lexical search is no longer the looser surface.** `search_evidence_fts` now applies the same visibility gate as vector search, from the same helper, so the two cannot drift apart again (`backend/src/contextedge/search/pg_fts.py:10, 65-79`, calling `vector_search._visibility_predicates`). It used to exclude role-blocked access policies and nothing else, which meant a record on legal hold or awaiting redaction was hidden from vector search and returned by lexical search — and because that function also matches raw ticket payload and a title `ILIKE`, it reached withheld records by substring, not just by embedding neighbourhood.

**What is still not exposed over HTTP:**

- There is **no** `GET /api/v1/evidence/{id}/chunks` endpoint. Chunk rows have no direct HTTP surface.
- `GET /api/v1/evidence?query=...` is **full-text only** — it routes into `search_evidence_fts`, never the semantic path (`backend/src/contextedge/api/v1/evidence.py:44-59`; `codewiki/KNOWN_GAPS.md:405-407`). Semantic/chunk search is reached internally by the hybrid ranker, knowledge retrieval and the agent-graph seed resolver, not by an API client.
- **`chunked_at` and `chunk_count` are not on the response schemas.** `EvidenceItemResponse` and `EvidenceItemDetail` do not declare them (`backend/src/contextedge/schemas/evidence.py:23-62`) — an earlier revision of this document said otherwise, and was wrong. They exist as columns only (`backend/src/contextedge/models/evidence.py:127-131`), read by the chunk task and by SQL, not by the UI.

See [codewiki/CHUNKING_DESIGN.md](../codewiki/CHUNKING_DESIGN.md) §6 for the search-integration design.

Introduced in migration `0030_evidence_chunks`.

## Episodes — review, AI first pass, and what approval triggers

Base path: `/api/v1/episodes`.

Implementation: `contextedge.api.v1.episodes`, `contextedge.schemas.evidence` (the episode schemas live there), `contextedge.workers.evaluation_tasks`.

An **episode** is a time-bounded narrative slice reconstructed from a correlated cluster of evidence. Reconstruction produces *drafts*; a human (or, optionally, the AI first pass) approves them.

### Listing

`GET /episodes` excludes `reviewer_state = "superseded"` unless you pass `include_superseded=true` or name the state explicitly (`backend/src/contextedge/api/v1/episodes.py:68-76`). This is deliberate and it matters: reconstruction replaces its own drafts as more of a thread arrives, and on the live graph 138 of 253 episodes (54%) were superseded rows. Shown next to current ones with only a status badge, they are indistinguishable from the answer — and the replaced draft is usually the *worse* one.

`sort=review_priority` orders by a computed priority ahead of `created_at` (`episodes.py:77-85`); anything else is a 422.

### `ai_review` — the AI first pass

`EpisodeResponse.ai_review` is a nullable JSON object carrying the AI reviewer's assessment: verdict, confidence, reasons, `auto_approved`, `failed_floors` (`backend/src/contextedge/schemas/evidence.py:108-112`, column added by migration `0070`). Advisory mode is pointless if the reviewer cannot see the verdict, so this field is what the review surface renders as the AI badge.

Modes come from the deployment setting `EPISODE_AI_REVIEW`, validated against `^(off|advisory|auto_approve)$` and defaulting to `off` (`backend/src/contextedge/config.py:185-187`):

| Mode | Behaviour |
| --- | --- |
| `off` | The hourly sweep is a no-op returning `{"status": "disabled"}`. It is still scheduled unconditionally, so enabling the mode needs no beat restart (`backend/src/contextedge/workers/celery_app.py:372-383`; `evaluation_tasks.py:171-173`) |
| `advisory` | Assess and annotate every pending draft; approve nothing |
| `auto_approve` | Also approve the subset that clears the deterministic floors |

`POST /api/v1/episodes/ai-review` dispatches the sweep for the caller's tenant (`episodes.py:556-607`), gated to `knowledge_manager`. Two rules:

- `advisory=true` **downgrades** the run to advisory for this dispatch only.
- With the setting at `off`, the dispatch always runs advisory-only. **An endpoint can run a weaker mode than configured, never a stronger one** (`episodes.py:583-591`).

The sweep itself (`backend/src/contextedge/workers/evaluation_tasks.py:125-358`) commits **per episode before any dispatch**, so one deadlock cannot re-cost fifty LLM calls (`evaluation_tasks.py:278-283`); aborts a tenant's batch after five consecutive transient failures rather than hammering a down provider (`:297-309`); and defers entirely while that tenant is actively ingesting, counting `deferred_tenants` instead of churning (`:195-203`).

> **Not a code path:** you may see `bulk_content_gate` in an `episodes.ai_review` payload. That is a marker written by a one-off operational database script on 2026-08-19 — not a review mode, not a feature. The code's modes are exactly `off` / `advisory` / `auto_approve`.

### What approval triggers

`POST /episodes/{id}/approve` and `POST /episodes/bulk-approve` (both `knowledge_manager`) set `status` and `reviewer_state` to `approved`, stamp `reviewer_user_id`, write an audit event — and then **commit explicitly before dispatching** (`episodes.py:255-261, 315-318`).

That ordering is not incidental. The signature task re-reads the episode and no-ops *without retry* when it is not yet approved, so a message consumed before the request's commit landed silently lost the signature; and a rollback after dispatch left tasks running for an approval that never happened. The request-scoped session commits again at request end — that second commit is an empty no-op.

After the commit, two dispatches fan out, each wrapped so a down broker cannot fail the approval:

1. `evaluation.extract_issue_signature` — approved stories mint their **issue signature** (`episodes.py:263-268`; `backend/src/contextedge/workers/signature_tasks.py:20-26`). One LLM call per approved episode, idempotent: an already-linked episode is a no-op, so a double-fired approval or a retry costs nothing.

   A signature is the structured shape of the problem — `affected_capability`, `failing_component`, `failure_mode`, `trigger_change`, plus optional `environment` and `scope` (`backend/src/contextedge/models/issue_signature.py:42-54`, migration `0045`). It is broader than an `ErrorSignature`'s exact error text and narrower than embedding similarity. Rows are deduped per tenant on `signature_key` (`uq_issue_signature_key`), so **episodes that share a signature form a recurrence chain** and `episode_count` is the recurrence counter. `EpisodeIssueSignature` is the join table, unique per `(episode_id, issue_signature_id)`, carrying a confidence (`issue_signature.py:66-95`).

   Similar problems, never the same occurrence — a recurrence chain is the answer to "has this happened before?", not "is this a duplicate ticket?". There is no HTTP surface for signatures of their own; they reach agents through the graph projection, rendered as `"component: failure mode"` labels, and through the seed layer that matches a query against their de-slugged text.
2. `pattern.cluster_episodes` for the episode's domain (`episodes.py:270-277`, and once per affected domain on bulk approve at `:330-337`). Passing `None` clusters nothing useful — a global pass only sees NULL-domain episodes — which is why the domain id is threaded through.

### Reconstruction

`POST /episodes/reconstruct` returns `202` with a `TaskDispatchResponse` and enqueues `extraction.reconstruct_episode` on the **`correlation`** queue (`episodes.py:342-347`). Automatic reconstruction is debounced 180 seconds after correlation creates edges, re-checks settlement at run time, and force-narrates a never-quiet cluster within 30 minutes of its oldest evidence.

## Execution approvals

Base path: `/api/v1/execution`.

Implementation: `contextedge.api.v1.execution`.

Governed playbook execution exposes three verbs on a pending approval request — **Approve**, **Deny**, and **Modify** — so reviewers can approve with changes instead of the binary approve/deny choice. Modify uses the same structured reason-code enum as reject so analytics can compare across verbs.

### `POST /execution/runs/{run_id}/approvals/{approval_id}/decide`

Existing endpoint. Body: `ApprovalDecision { decision: "approved" | "denied", comment? }` — any other value is a `400` (`services/execution_service.py:1338-1339`). Requires `domain_admin`. The approval row is read `SELECT ... FOR UPDATE`, so two concurrent decide/modify calls on the same approval serialise instead of both passing the pending check (`:1327-1336`).

It writes an `approved_by` / `denied_by` graph edge (`:1429-1438`) and a first-class `Decision` whose `decision_type` is the **decision string verbatim** — `"approved"` or `"denied"`, not `"approve"`/`"deny"` (`:1444`). Worth knowing before you filter: `INTENT_BY_DECISION_TYPE` is keyed on `approve` / `deny` / `modify`, so a decision minted here does not match it and lands with `decision_intent` NULL. `decision_type` filtering is exact match, so `GET /decisions?decision_type=approve` will not return the rows this endpoint creates — query `decision_type=approved` (or `denied`) instead.

Returns `400` if the request is already decided, `404` if missing.

### `POST /execution/runs/{run_id}/approvals/{approval_id}/modify`

Approve-with-changes on a pending approval request.

Request body (`ApprovalModificationRequest`):

```json
{
  "modification_diff": { "inputs": { "ttl_days": 30, "notify": true }, "summary": "shorter ttl" },
  "modification_reason_code": "plan_incomplete",
  "comment": "per cert policy"
}
```

Valid `modification_reason_code` values are the same `REJECTION_REASON_CODES` enum used by reject. `modification_diff` must be a non-empty object.

Behavior:

- `ApprovalRequest.status` flips to `modified`; `modification_diff`, `modification_reason_code`, `decision_comment`, `decided_by`, and `decided_at` are stamped.
- If `modification_diff.inputs` is a dict, it is merged into the step run's `inputs` JSONB (shallow merge, new keys win).
- The execution run and step transition from `awaiting_approval` back to `running` — modify is treated as approved-with-changes, not a new approval cycle.
- An operational event `approval.modified` is emitted with `modification_reason_code` and the diff keys tagged.
- A `modified_by` graph edge is added from the approval request to the deciding user, with `safety_class`, `execution_run_id`, and the reason code in metadata.
- A first-class `Decision(decision_type="modify", actor_type="human")` is created with two `DecisionOption`s: the original action (`selected=false`, `rejection_code=<reason>`) and the modified action (`selected=true`). This keeps the graph's `considered`/`chose` invariant intact alongside approve and reject paths.

Requires `domain_admin`. Returns `400` for invalid codes, empty diffs, or already-decided requests. Returns `404` when the approval request is missing.

### The step-level ledger

Two endpoints expose the per-step ledger to an external executor (shipped 2026-08-16; before that the service functions existed with no route and no caller, so every control in the chain was unreachable — `codewiki/KNOWN_GAPS.md`):

| Method | Path | What it records |
| --- | --- | --- |
| `POST` | `/execution/runs/{run_id}/steps/{step_run_id}/invocations` | One tool call the executor made for this step |
| `POST` | `/execution/runs/{run_id}/steps/{step_run_id}/complete` | Closes the step; an `error_message` records it as failed |

Both sit on the same gate as abort and complete — the run's initiator or `domain_admin` — and the step must belong to the run named in the URL.

Three deliberate design choices worth respecting in a client:

- **Refusals are `409`, not `500`.** A duplicate replay and a stale artifact binding are well-formed requests that the *state* declines. The approved artifact is re-checked at the last moment before an invocation is accepted, and a step already recognised as a duplicate is refused.
- **The request body carries no attempt number and no idempotency key.** Both are derived from what is already recorded. A caller that can hand in the key the duplicate check tests against can defeat the check by asserting the answer.
- **An invocation may not declare a higher safety class than its own step.** Without that rule a destructive call could be recorded under a step approved as read-only, with every upstream control still reading as satisfied. It is refused in the service, so any caller inherits it.
- **A step still awaiting approval cannot be reported complete** — otherwise `complete_execution`'s open-steps check would pass with an undecided approval sitting under it.

**There is still no executor.** These endpoints make the ledger *drivable*; nothing in this repo drives it, and nothing schedules or resumes a run. All six MAF tools are read-or-propose, so `execution_service` is a ledger waiting on external callers — and a caller that stops calling leaves a run open (`codewiki/KNOWN_GAPS.md:34`).

### What `POST /decisions` writes

One HTTP call, six side effects, all inside `create_decision` (`backend/src/contextedge/services/decision_trace_service.py:51-243`):

1. **The `decisions` row.** `decision_intent` is derived from `decision_type` via `INTENT_BY_DECISION_TYPE`; an explicit argument wins, and an unknown explicit value raises rather than being stored. `risk_level` comes from the **selected** option only — never the riskiest one considered (`:86-103`). `policy_result` is whatever the caller passes; when the execution service creates the decision it fills it with the *strictest* action-policy verdict across the run's steps, and NULL when no policy produced one at all (`backend/src/contextedge/services/execution_service.py:198-203, 1005`).
2. **`decision_options` rows**, one per option offered (`:145-159`).
3. **Graph edges**, all through `ensure_edge` so a retry cannot duplicate them: `based_on` to each typed evidence / episode / pattern ref, `considered` for every option plus `chose` for the selected one, `applied_policy` per policy ref, and `followed_by` when the decision is chained to a parent (`:163-185`).
4. **A session trail entry** — `append_trace_event(event_type=f"decision.{decision_type}")` writes a `decision_trace_events` row and an operational event (`:187-197`).
5. **Operational event `decision.created`** tagged `memory_class="reasoning"` (`:199-215`).
6. **An inline embedding** — `embed_decision(...)` fills `decisions.embedding` so the row is immediately findable by `/decisions/similar`. If the provider fails, `decision.embed_failed` is logged and the decision lands with a NULL embedding; it still participates in *structural* search, just not semantic ordering (`:217-237`).

Then the review-context cache for the session is invalidated (`:239-240`).

Two caveats to carry: there is **no backfill task for decision embeddings**, so a row that lands NULL stays NULL until it is rewritten (`codewiki/KNOWN_GAPS.md:320`); and invalidation fires post-flush but pre-commit, leaving a narrow window in which a concurrent read can re-populate the cache from the pre-commit snapshot — the 300-second TTL is the backstop (`codewiki/KNOWN_GAPS.md:328`).

### `POST /decisions/{id}/reject`

Rejects an AI-recommended decision with a **structured reason code** so the feedback feeds analytics instead of getting lost in free-text.

Request body:

```json
{
  "code": "wrong_diagnosis",
  "comment": "evidence contradicts restart hypothesis"
}
```

Valid `code` values (`contextedge.models.decision.REJECTION_REASON_CODES`):

- `wrong_diagnosis`
- `plan_incomplete`
- `needs_human_judgment`
- `user_context_missing`
- `policy_violation`
- `other`

Behavior:

- The currently selected `DecisionOption` is stamped with `rejection_code` + `rejection_reason = comment` and flipped to `selected = false`.
- A `DecisionOutcome` is created with `execution_result = "rejected"`, `feedback_code = code`, `action_executed = "rejected_by_reviewer"`, and a `resulted_in` graph edge. The outcome carries `feedback_by = <actor_id>` from the caller identity.
- `decision.status` flips to `superseded` and `decision.human_override = true`.
- An operational event `decision.rejected` is emitted with the code + comment tagged for analytics.

Returns `201` with the new `DecisionOutcome`. Returns `400` for unknown codes, `404` when the decision is missing.

### `GET /decisions/similar`

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `decision_type` | string | yes | Required filter |
| `workflow` | string | no | Match on `context_snapshot.workflow` |
| `environment` | string | no | Match on `context_snapshot.environment` |
| `impacted_dependency` | string | no | Match on `context_snapshot.impacted_dependency` |
| `query_decision_id` | UUID | no | When set, results are ordered semantically using this decision's stored embedding as the query vector (pgvector cosine distance). Self is excluded. |
| `query_text` | string | no | Free-text query embedded on the fly and used as the query vector. Ignored when `query_decision_id` is set. |
| `limit` | int (1–50) | no | Max results, default 10 |

**Ordering:**

- When a query embedding resolves (from `query_decision_id`, that decision's stored embedding; or `query_text`, embedded on the fly), results are ordered by `embedding <=> query` cosine distance and the query is constrained to decisions that have an embedding of their own.
- Otherwise, results fall back to `created_at DESC` ordering. Provider failures during query-text embedding are swallowed and degrade to the fallback path — never 500 the caller.

JSONB containment on `workflow` / `environment` / `impacted_dependency` is applied in both paths as a structural pre-filter, so semantic retrieval can still be scoped to "find the most semantically similar VPN decisions in prod". Paired with `GET /decisions/effectiveness` this renders the "based on N similar tickets, X% succeeded" provenance line — or use `/decisions/similar/aggregate` below for the same three-way join in a single round trip.

### `GET /decisions/similar/aggregate`

Top-N similar decisions + total count + outcome aggregate + success rate, composed server-side so Zone 5 can render provenance in one request instead of fanning out across `/similar`, `/effectiveness`, and a separate count call.

Same query parameters as `/decisions/similar` (`decision_type` required, optional `workflow` / `environment` / `impacted_dependency` / `query_decision_id` / `query_text` / `limit`). Semantic ordering applies to the `decisions` list; `total_count` and `outcomes` remain scoped to `decision_type` + structural context filters only (they are aggregate metrics over the structural slice, not the semantic ordering).

Response shape (`SimilarDecisionsAggregateResponse`):

```json
{
  "decision_type": "execute_playbook",
  "context_filters": { "workflow": "vpn", "environment": "prod" },
  "total_count": 143,
  "outcomes": { "success": 124, "failure": 12, "rejected": 7 },
  "success_rate": 0.867,
  "decisions": [ /* up to limit DecisionResponse items */ ]
}
```

`success_rate` is `success / sum(counted)` where counted outcomes are `success|failure|partial|timeout|rejected`. Unknown outcome labels are preserved in `outcomes` but excluded from the denominator so a rogue label can't skew the ratio. `success_rate` is `null` when no outcomes are recorded.

### `GET /decisions/effectiveness`

Same filter keys as `/decisions/similar`. Returns `{decision_type, context_filters, total, outcomes}` where `outcomes` is a count map over `DecisionOutcome.execution_result` values (`success`, `failure`, `partial`, `timeout`, `rejected`).

| `no_cache` | bool | no | When `true`, skips the Redis read-through cache but still warms on return |

Read-through cached on Redis under `review_queue:{tenant_id}:{session_id}` with `REVIEW_CONTEXT_CACHE_TTL_SEC = 300` (`backend/src/contextedge/services/review_queue_service.py:35`). The `review_queue.prefetch_review_context` Celery task warms the cache on session creation (`services.session_service.create_resolution_session`) and is explicitly routed to the `default` queue so its short task name is not swallowed by the module-path catch-all (`backend/src/contextedge/workers/celery_app.py:273-276`). The first request after `POST /sessions` therefore hits Redis, not Postgres.

On cache miss the handler live-computes via `build_review_context` and back-fills (`backend/src/contextedge/api/v1/review_queue.py:61-78`). Both cache reads and writes are wrapped so a corrupt entry or a Redis outage degrades to live compute rather than 500-ing the caller (`review_queue.py:83-105`).

Caching only engages when the request uses **default** limits — 20 / 10 / 20. Passing custom `decisions_limit` / `execution_runs_limit` / `events_limit` bypasses the keyed slot entirely, so the cached payload can never be poisoned by a shape it does not claim (`review_queue.py:46-52`).

Every mutation that changes a session's review state invalidates the cached bundle via `services.review_queue_service.invalidate_review_context`: `POST /decisions`, `POST /decisions/{id}/outcome`, `POST /decisions/{id}/reject`, `POST /execution/runs/{run_id}/approvals/{approval_id}/decide`, `POST /execution/runs/{run_id}/approvals/{approval_id}/modify`, and `POST /sessions/{id}/close`. Approve and Modify invalidate transitively through their embedded decision creation. Invalidation fires post-flush but pre-commit, so a narrow race window exists where a concurrent read could re-populate the cache with the pre-commit snapshot; the 300s TTL is the backstop.

Response shape (`ReviewQueueContext`):

```json
{
  "session": { "id": "...", "status": "open", "symptoms": [...], "entities": [...], ... },
  "top_decision": { /* DecisionResponse with options + outcomes */ },
  "top_decision_badge": { "score": 0.92, "level": "green" },
  "similar": {
    "decision_type": "execute_playbook",
    "context_filters": { "workflow": "vpn", "environment": "prod" },
    "total_count": 143,
    "outcomes": { "success": 124, "failure": 12, "rejected": 7 },
    "success_rate": 0.867
  },
  "decisions": [ /* up to decisions_limit */ ],
  "execution_runs": [ /* up to execution_runs_limit */ ],
  "recent_events": [ /* up to events_limit */ ]
}
```

Selection rules:

- **`top_decision`** — latest pending decision with a confidence score; falls back to latest decision with a confidence score; falls back to the latest decision overall; `null` when the session has no decisions.
- **`top_decision_badge.level`** — server-derived thresholds so every consumer agrees: `green >= 0.8`, `amber 0.5–0.8`, `red < 0.5`, `null` when the decision has no confidence recorded.
- **`similar`** — filters are derived from `top_decision.context_snapshot` keys (`workflow`, `environment`, `impacted_dependency` only); composed from `count_similar_decisions` + `get_decision_effectiveness`; `null` when no `top_decision` exists.
- **`similar.success_rate`** — `success / sum(counted_outcomes)` where counted outcomes are `success|failure|partial|timeout|rejected`; unknown outcome labels are ignored so they can't skew the denominator; `null` when no outcomes are recorded.

Returns `404` when the session does not exist.

## Admin — how LLM usage gets recorded

Base path: `/api/v1/admin`. (Endpoint-by-endpoint reference is in §"Admin — cost, budget and pipeline health" further down; this section explains where the numbers come from.)

Implementation: `contextedge.api.v1.admin_cost`, `contextedge.services.admin_cost_service`, `contextedge.ai.observability`.

Every LLM call in the engine flows through `record_llm_usage` (`ai/observability.py`) which emits:

1. **Prometheus counters** — `contextedge_llm_tokens_total` (labelled by `tenant_id`, `model`, `task`, `token_type ∈ {prompt,completion,cached}`) and `contextedge_llm_requests_total` (labelled by tenant, model, task, `outcome ∈ {ok,error}`). Scrape via `/metrics`.
2. **Structured logs** — one `llm.usage` log line per call with full token breakdown + duration.
3. **Operational events** — persisted row with `event_type="llm.usage"`, queried by the admin dashboard.

Cache-hit tokens are normalised across providers: OpenAI `usage.prompt_tokens_details.cached_tokens` and Anthropic `usage.cache_read_input_tokens` both land in a single `cached_tokens` counter.

### `GET /admin/llm-usage`

Returns aggregated token spend + cache-hit rate + model×task breakdown for the caller's tenant over a configurable window.

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `window_hours` | int (1–720) | no | Aggregation window, default 24. Max 30 days. |
| `top_n_breakdown` | int (1–50) | no | How many model×task rows to return (ranked by cost desc), default 10. |
| `all_time` | bool | no | Ignore the window entirely — "overall to date" is a different question from a rolling window, and the window caps at 30 days (`backend/src/contextedge/api/v1/admin_cost.py:49, 74-77`). |
| `sync_run_id` | UUID | no | Scope to one sync run's own start/end. Answers "what did **that** cost" rather than "what happened in a window that contains it". A run still going has no end yet, which is what makes the meter live. Foreign or unknown run -> 404 (`admin_cost.py:50-73`). |

Response shape (`LlmUsageResponse`):

```json
{
  "window_hours": 24,
  "from_time": "...",
  "to_time": "...",
  "totals": {
    "request_count": 1523,
    "prompt_tokens": 842000,
    "completion_tokens": 95000,
    "cached_tokens": 620000,
    "total_tokens": 937000,
    "estimated_cost_usd": 1.83,
    "cache_hit_rate": 0.736
  },
  "by_model_task": [
    {
      "model": "gpt-4o-mini",
      "task": "classification",
      "request_count": 1200,
      "prompt_tokens": 600000,
      "completion_tokens": 30000,
      "cached_tokens": 480000,
      "total_tokens": 630000,
      "estimated_cost_usd": 0.042
    }
  ]
}
```

Cost estimates derive from a rate table in `services.admin_cost_service.MODEL_COST_USD_PER_M_TOKENS`. Non-authoritative — the LLM provider's billing dashboard is the invoice of record. Cache-hit rate = `cached_tokens / prompt_tokens` (0 when no prompt tokens in window).

Requires `tenant_admin` or `platform_super_admin`. Paired with the frontend `/admin/cost` dashboard.

## Worked example — the Acme VPN incident through the API

The same incident every ContextEdge doc uses. Tenant **Acme Corp**; the corporate VPN gateway `vpn-gw-east-01` fails; ServiceNow incident `INC0010427` is raised, duplicates follow, people chat in Teams, and an engineer emails a root-cause note. Here is which call does what, in order.

**1. Connect and approve the source.**

```
POST  /api/v1/sources                          -> Source (servicenow)
POST  /api/v1/sources/{id}/discover            -> [SourceObject] (incident, kb_knowledge, …)
PATCH /api/v1/sources/{id}/objects/{obj_id}    body: {"approved_for_sync": true}
```

Approving for sync dispatches `sync.run_incremental_sync` immediately (`api/v1/sources.py:280-282`); beat then re-dispatches it every 15 minutes.

**2. Backfill the history, and watch the meter.**

```
POST /api/v1/sources/{id}/backfill             -> {"status":"queued","task_id":"…"}
GET  /api/v1/admin/llm-usage?sync_run_id=<run> -> what THIS run has cost so far
GET  /api/v1/admin/pipeline-health             -> queue depths + the graph chain
```

Provision a `tenant_llm_budgets` row first. Without one the 2M-token deployment default applies and a long backfill stops mid-run with `block`.

**3. Watch the fan-out land.** `INC0010427` becomes a `RawEvidenceObject` (payload over 32 KB goes to MinIO, leaving a stub), then an `EvidenceItem`, then chunks, then correlation edges. `GET /api/v1/evidence?query=INC0010427` finds it even though it is a full-text search — `search_evidence_fts` has an explicit fallback that matches the ticket number inside `raw_evidence_objects.raw_payload` (`ticket_number` / `ticketNumber` / `number`) and on `RawEvidenceObject.external_id` (`backend/src/contextedge/search/pg_fts.py:50-60`), so a reviewer can search by the number on the ticket. Note the payload half of that fallback goes blind on offloaded records: once a payload passes 32 KB the column holds only the `{"_offloaded": true, …}` stub, so the JSON key lookups match nothing and only the `external_id` clause still fires.

**4. Correlation joins the thread.** The engineer's email quoting `INC0010427` links to the ServiceNow incident at confidence **1.0** through the ticket-number bridge; a Teams message naming `vpn-gw-east-01` the same week links at **0.75** as a rare device. `GET /api/v1/correlations?evidence_id=<id>` lists them; `POST /api/v1/correlations/{id}/decision` is how a reviewer accepts, rejects, splits or merges.

**5. An episode is reconstructed and reviewed.**

```
GET  /api/v1/episodes?sort=review_priority     -> drafts, superseded ones hidden
GET  /api/v1/episodes/{id}                     -> steps, evidence, contradictions, ai_review
POST /api/v1/episodes/{id}/approve             -> knowledge_manager
```

Approval commits first, then dispatches the issue signature and domain clustering. The signature for this one is roughly `affected_capability: "remote-access"`, `failing_component: "vpn-gw-east-01"`, `failure_mode: "certificate-expired"` — and when the certificate expires again next year, the second episode joins the same `signature_key` and `episode_count` becomes 2. That counter is what "this has happened before" is made of.

**6. Knowledge becomes a playbook.**

```
POST /api/v1/patterns/cluster?domain_id=<network>
POST /api/v1/playbooks/generate                -> candidate from the pattern
POST /api/v1/playbooks/{id}/transition         -> draft -> approved
```

Generation retrieves Acme's own "VPN gateway certificate renewal" SOP and cites it, warning-tagged if that article is contested or superseded rather than hiding it.

**7. Runtime answers the next VPN ticket.**

```
POST /api/v1/runtime/match
  {"symptoms": ["users cannot connect to VPN"],
   "entities": ["vpn-gw-east-01"],
   "session_id": "…"}
-> {"match_id": "…", "results": [ … ], "filters_applied": { … }}

GET  /api/v1/runtime/explain/{match_id}        -> the scoring breakdown, 1h TTL
POST /api/v1/runtime/feedback                  -> whether it helped
```

An empty `results` array here means the ranker **abstained** — every candidate scored under 0.35 — not that the filters excluded everything.

**8. The reviewer console reads it all in one call.**

```
GET /api/v1/review-queue/{session_id}/context
```

Session header, top pending decision with its confidence badge, the similar-decision aggregate ("based on 143 similar tickets, 87% succeeded"), scoped decisions, execution runs and recent events — one round trip, Redis-cached for 300 seconds.

**9. Retention eventually reclaims it.** `INC0010427`'s evidence carries resolved identities, so it classifies as *long-term* memory and is archived after `max(base x 6, 180)` days rather than the short-term `base` — 2,190 days at the default 365-day base (`backend/src/contextedge/services/memory_service.py:64-79`). A drive-by Teams message with no identities archives at 365.

## Observability

Three unversioned endpoints, none of them behind auth (`backend/src/contextedge/main.py:168-210`):

| Endpoint | What it answers | Behaviour |
| --- | --- | --- |
| `GET /health` | "Is the process alive?" | Pure liveness. No dependency is touched (`main.py:173-177`) |
| `GET /ready` | "Can it serve traffic?" | Probes the database (`SELECT 1`), the **migration head**, and Redis, each with a 5-second timeout. Any failure returns **503** with a per-check dict (`main.py:179-210`) |
| `GET /metrics` | Prometheus scrape | Mounted via `Instrumentator().instrument(app).expose(app)` (`main.py:168`) |

Two `/ready` details worth knowing:

- **Object storage is reported but does not gate readiness.** It shows as `ok` or `degraded`, because blob access is lazy and most request paths work without it (`main.py:179-210`; MinIO bucket setup only degrades at startup, `main.py:44-59`).
- **The migration check compares `alembic_version` to the head of the bundled scripts** and 503s on a mismatch. An installed layout that ships no alembic directory reports the check as explicitly *disabled* rather than quietly passing (`main.py:89-106`). Workers enforce the same rule harder — `_require_migrations_at_head` raises `SystemExit` at worker startup rather than let a stale schema corrupt ingestion mid-transaction (`backend/src/contextedge/workers/celery_app.py:83-139`).

Never quote a migration head number in prose. Trust `alembic heads` (`docs/RUNBOOK.md` §14, "Maintenance Rules").

Beyond HTTP, three streams carry runtime behaviour:

- **`operational_events`** — the append-only domain event log (`backend/src/contextedge/models/events.py:13-61`), written through `append_operational_event`, which fills `correlation_id` / `causation_id` / `actor_id` from the request context automatically (`backend/src/contextedge/services/event_log_service.py:32-61`). Read back with `list_operational_events`, newest-first, default limit 100 (`event_log_service.py:64-85`).
- **`audit_logs`** — who changed what, written by `RequestAuditMiddleware` for every mutating `/api/v1` call plus explicit `log_audit_event` calls at governance points such as sync control and episode approval. Exposed at `GET /api/v1/audit-logs`.
- **structlog lines** — always emitted, including for the unauthenticated 401 probes that never resolve a tenant and therefore never reach `audit_logs`.

## Admin — cost, budget and pipeline health

Base path: `/api/v1/admin`. Every route calls `user.require_role("tenant_admin")`, which the `has_role` super-role rule also satisfies for `platform_super_admin` and `admin`. All four are tenant-scoped: a caller only ever sees or edits their own tenant's rows, regardless of role (`backend/src/contextedge/api/v1/admin_cost.py:60, 106, 118, 142, 175`).

### `GET /admin/llm-usage`

Aggregated token and estimated-USD spend plus a top-N `(model, task)` breakdown. Parameters and response shape are in the section above. Reads `operational_events` rows with `event_type = "llm.usage"` written by `ai/observability.record_llm_usage` — there is no second aggregation column to drift out of sync. Cache-hit rate is `cached_tokens / prompt_tokens`; expect above 0.5 once workers are warm.

### `GET /admin/tenant-budget`

Returns the caller's tenant's `TenantLLMBudget` row — daily token limit, daily USD cap, `action_on_exceed` in `{"block", "warn"}` — or `null` when no row exists (`admin_cost.py:102-110`).

**`null` does not mean uncapped.** A tenant with no row falls through to deployment defaults: `DEFAULT_DAILY_TOKEN_LIMIT` 2,000,000 tokens, `DEFAULT_DAILY_COST_CAP_USD` $25.00, `DEFAULT_BUDGET_ACTION_ON_EXCEED` `block` (`backend/src/contextedge/config.py:191-198`). `check_budget` applies them through a `_DefaultBudget` stand-in that takes the identical evaluation path, deliberately without persisting a row (`backend/src/contextedge/services/tenant_budget_service.py:107-121, 249-279`). Only setting both defaults to `None` in config restores genuinely unlimited spend, reported as `reason="no_budget"`.

This has bitten a real backfill: the 2M-token default froze a live 84-ticket Zoho run mid-way. Provision a real row (thread-heavy tickets run roughly 100k tokens each) or set `action_on_exceed: "warn"` for the window before a bulk ingest (`docs/RUNBOOK.md` §7.12, "Onboarding a new tenant / bulk backfill").

### `PUT /admin/tenant-budget`

Body: `{daily_token_limit: int|null, daily_cost_cap_usd: float|null, action_on_exceed: "block"|"warn"}`. Creates or replaces the row and invalidates the usage cache (`admin_cost.py:113-134`; `tenant_budget_service.py:333-372`). Nulls mean "don't cap on this axis" — at least one of the two must be set for the row to do anything. Validation failures come back as 400.

- `action_on_exceed = "warn"` — the call proceeds and an `llm.budget_warning` operational event is written, which makes the overspend queryable after the fact.
- `action_on_exceed = "block"` — `llm_complete` raises `TenantBudgetExceeded` **before** spending, so callers can degrade (`backend/src/contextedge/ai/provider.py:231-279`).

The token limit is checked before the cost cap, so a tenant that only sets a token cap never sees `cost_cap_exceeded` (`tenant_budget_service.py:240-243`).

### `GET /admin/tenant-budget/status`

Live view combining budget config with the current UTC day's usage, computed fresh — `check_budget(..., use_cache=False)` (`admin_cost.py:137-163`).

Response: `budget` (the row, or null), `current_tokens`, `current_cost_usd`, `allowed`, `reason` (`ok` | `no_budget` | `token_limit_exceeded` | `cost_cap_exceeded`), `effective_token_limit`, `effective_cost_cap_usd`, and `limit_source` — `"tenant"` when a row exists, `"default"` when the deployment defaults are doing the work, `"none"` when nothing caps (`admin_cost.py:148-163`). `limit_source` is the field that tells a dashboard whether a cap is the operator's or the platform's.

Three implementation notes that explain surprising numbers, all in `services/tenant_budget_service.py`:

- The pre-call gate caches usage for 60 seconds (`USAGE_CACHE_TTL_SECONDS`, `:51`), so at most one over-cap call slips through per minute. This endpoint bypasses that cache; the gate does not.
- Concurrent checks are serialised by a per-tenant `asyncio.Lock` held in a `WeakKeyDictionary` **keyed per event loop** (`:53-90`). A single flat dict made the first task's loop own every lock and killed a 499-task sweep with "bound to a different event loop".
- Cross-worker races are unbounded pending a Redis counter (`:60-63`). An `after_delete` listener evicts the cache when a budget row is deleted (`:173-184`).

### `GET /admin/pipeline-health`

Queue depths, throughput, latency and the graph chain in one read (`admin_cost.py:166-178` -> `backend/src/contextedge/services/pipeline_health_service.py:87`). Separate from `/llm-usage` because the question is different: that one asks what the run cost, this one asks whether it is getting anywhere. A run can spend steadily and produce nothing, and that is exactly the failure this exists to make visible.

Mechanism:

- Redis `LLEN` per lane over all eight queues in pipeline order — `extraction, correlation, embedding, hydration, pattern, evaluation, sync, default` (`pipeline_health_service.py:43-52`).
- `HLEN unacked` for in-flight work. This matters more than it sounds: during the reconstruction phase *all* remaining work lives there, and 5,800 debounced reconstructs once churned for hours while every queue read zero (`pipeline_health_service.py:58-84`).
- `BACKLOG_ALERT_DEPTH = 500` (`:55`).
- One SQL read counts the graph chain end to end — evidence, embedded, identities, and onward — so **the first zero in the sequence is the diagnosis** (`:87-110`).
- Never raises on broker failure; returns empty depths instead (`:82-84`).

The module docstring records the incident that created it: every per-task metric reported healthy while `correlate_evidence` starved behind 8,000 normalizations and episodes stayed at zero (`pipeline_health_service.py:1-27`). Rendered at `/admin/pipeline` in the UI.

**Diagnosing "ingest ran but nothing is retrievable":** two signatures look identical from the evidence table and are told apart here.

- *Budget block.* Chunks sit at `embedding IS NULL` and there is **no `llm.usage` event at all** for the missing work — `check_budget` raises `TenantBudgetExceeded` *before* the call, so a blocked call is never recorded as usage. (`llm.usage` only ever carries `outcome` `ok` or `error`; nothing in the backend writes `budget_exceeded`.) Confirm it with `GET /admin/tenant-budget/status`, which returns `allowed: false` and a `reason` of `token_limit_exceeded` or `cost_cap_exceeded`; on `warn` tenants the day's `llm.budget_warning` operational events are the trail.
- *Missing consumer.* Chunks sit at `embedding IS NULL` and the `embedding` queue depth never moves — check that the worker fleet consumes all eight queues (`docs/RUNBOOK.md` §7.1).

## Shared response shapes

Endpoints that used to return bare dicts now declare `response_model=` against three shared Pydantic shapes in `contextedge.schemas.common`. Callers can rely on these for frontend type generation instead of hand-maintaining the shape. The authoritative per-endpoint mapping is the `**Response**` line for each entry in [10_API_Documentation.md](10_API_Documentation.md).

- **`StatusResponse { status: str, detail?: dict }`** — minimal past-tense ack. Declared by `PATCH /evidence/{id}/relevance` (`status="updated"`), `POST /correlations/{id}/decision` (`status ∈ accepted|rejected|split|merge`, `detail` carries correlation_id + replacement_ids when relevant), `POST /correlations/suggestions/{id}/reject`, `POST /correlations/fleet-suggestions/{id}/reject`, and `POST /identities/merge-proposals/{id}/decide`.
- **`TaskDispatchResponse { status: str, task_id?: str, detail?: dict }`** — enqueue ack. Declared by `POST /sources/{id}/backfill`, `POST /sources/local-ingest`, `POST /threads/{id}/hydrate`, `POST /episodes/reconstruct`, `POST /episodes/ai-review`, `POST /patterns/cluster`. `task_id` is populated whenever the dispatch returned one; `detail` carries task-specific supplemental info (`{"object_count": 12}`, `{"evidence_count": 20, "domain_id": "…"}`, `{"mode": "advisory", "limit": 100}`). **One of these does not enqueue:** `POST /sources/local-ingest` normalizes each file inline and returns `status="ingested"` with no `task_id` — deliberate, to sidestep Celery worker lag on Windows (`backend/src/contextedge/api/v1/sources.py:530-566`). Do not read the shape as a promise of asynchrony.
- **`MutationAckResponse { status: str, id: str }`** — create/update ack with the affected entity's UUID. Declared by `POST /runtime/feedback` (`status="feedback_recorded"`, `id` = new `RetrievalFeedback.id`).

A number of endpoints still return bespoke raw dicts on purpose. Among them: `GET /patterns/{id}/graph`, `GET /decisions/effectiveness`, the graph reads (`/neighbors`, `/subgraph/...`, `/stats`, `/cmdb-topology`, `/change-risk`, `/fix-applicability`, `/edge-proposals` and its approve/reject verbs), `GET /sessions/{id}/history`, `GET /playbooks/{id}/references`, the correlation-suggestion reads (`/correlations/fleet-suggestions`, `/correlations/suggestions/stats`), `POST /sources/{id}/probe-config`, `POST /sources/{id}/sync/control`, and `GET /admin/pipeline-health`. They carry rich, observability-shaped payloads that deserve their own schemas rather than being squeezed into one of the three above. Frontend has matching local types in `frontend/src/lib/types/index.ts`.

To confirm which shape any endpoint returns today, read the generated inventory rather than this list — it comes straight from the OpenAPI schema and cannot drift.
