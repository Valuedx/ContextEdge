# Implementation Review — 2026-04

In-depth review of the ContextEdge implementation as of commit `35d44e2` on `integration/demo-aeops`. Three axes: **functionality** (does each piece do its job end-to-end), **consistency** (are patterns applied uniformly), **logic** (are invariants correct under edge cases).

This is a review **document**, not a plan or a task list. The plan that produced it lives in the chat that commissioned the work. Actions (`Critical` + `Important` findings) exit this document as TaskCreate entries in a follow-up pass.

> **Status update:** All four critical findings (F-04, F-09, F-17, F-23) plus F-22 as a bonus fix have shipped. See the Shipped section in §1 for the commit and test references. 17 important findings and 11 nice-to-haves remain as backlog — the doc is still the canonical map.

## Scope

**In scope:**

- Backend — all of `backend/src/contextedge/` (API routers, services, workers, models, middleware, AI layer, search, graph).
- Backend tests — structure, coverage gaps, consistency of `P0/P1/P2` prefixing.
- Frontend — `frontend/src/app/(dashboard)/*` pages, `frontend/src/lib/*`, shared components under `frontend/src/components/`.
- Migrations `0001` through `0025`.
- Documentation — `codewiki/*`, `docs/*`, root `*.md`.

**Out of scope:**

- Connector vendor APIs (Gmail/Teams/ServiceNow/Jira) are treated as external contracts; adapter behaviour is in scope but upstream semantics are not.
- Infrastructure (Docker Compose, MinIO, Redis, Postgres configuration).
- Third-party libraries and their internals.
- Performance benchmarking under load (this review reads code, does not run load tests).

## Severity rubric

| Level | Meaning | Examples |
|---|---|---|
| **Critical** | Data loss risk, auth bypass, or silently wrong behaviour that users would never catch from the UI. Ship a fix within a day. | Tenant isolation bypass, missing legal-hold check on purge, budget gate that never fires, SSR of secret data. |
| **Important** | Works today but will break at scale, in a known edge case, or under a specific failure mode. Ship within the current week. | Unbounded query, race window on dedupe, retry storm under provider 5xx, non-idempotent Celery task. |
| **Nice-to-have** | Inconsistency, dead code, small logic quirk, clarity issue. No deadline — backlog. | Log field name varies (`tid` vs `tenant_id`), unused helper, test file missing `P` prefix. |

A finding escalates one level when it's **silent** (no log, no exception, no metric). Silence in the face of wrongness is worse than the wrongness itself because it can't be operationally detected.

## Finding format

```
[SEV] <short title>
  location: <path:line> (or <path> for file-level)
  axis:     functionality | consistency | logic
  observation: <1-3 sentences on what's wrong or risky>
  evidence:    <grep hit, trace, or test that demonstrates it>
  fix:         <1 sentence on the smallest change that resolves it>
```

Every finding must have `location` pointing at a real file+line. Anything without a concrete location is a speculation, not a finding, and belongs in the "Observations" section of the report instead.

## Non-goals

- **Not a refactor.** The review identifies what's wrong, not what's merely different from how I'd do it. "Could be cleaner" ≠ finding.
- **Not a test audit.** Gaps in test coverage are noted as context, but this review isn't "here are tests we should write."
- **Not a second architecture review.** `ENTERPRISE_ARCHITECTURE_REVIEW.md` already did the strategic read. This review is tactical and ground-truth.
- **Not a style gate.** Python formatting / lint style is out of scope except where it hides a logic issue.

1. **Executive summary** — headline counts per severity, and the 3-5 findings the user should read if they read nothing else.
2. **Functionality** — per-flow trace findings (Phase 2 output).

### Read this if nothing else

The four items that justify a same-week fix before they burn a customer:

1. **F-04 (critical)** — Legal-hold evidence can land in the episode-reconstruction LLM prompt. Retention correctly excludes it with a SQL `WHERE`; the episode-evidence-build loop does not. One-line filter to add in `extraction_tasks.py::_reconstruct`.

2. **F-17 (critical)** — `soft_purge` mode claims "content unrecoverable" but leaves `canonical_entity_refs` (which contains extracted person / service names) on the row. Customers asking for GDPR-style scrub get a half-done job without any sign of it. One-line additional `NULL` in `retention_service.py::purge_archived_evidence`.

3. **F-09 (critical)** — Runtime `/explain` cache has a 3600s TTL but is never invalidated on playbook `transition_playbook`. A reviewer who transitions a playbook to `restricted` will still see the old match + details in cached explains for up to an hour. Invalidate on transition, or version-stamp the cache key.

4. **F-23 (critical)** — Contradiction scan doesn't filter out legal-hold evidence from its candidate set. Same shape as F-04; fix alongside it and share a helper.

These four share a theme: **legal-hold + GDPR scrub + cached derived state are the three places where a missed edge case turns into a compliance or security incident**, and all three have a gap. The code is otherwise tidy; these stand out.

### Next-tier (important, same-month)

**L-01 (ORM-DDL drift)** is a class of issue, not just one finding. Any FK tightening added to a model after `0001_initial` shipped doesn't land on older DBs. Worth one dedicated pass to audit every `ondelete=`, `nullable=False`, `unique=True` added post-`056eb846` and ship a single consolidation migration.

**F-11 (cross-tenant step_run in approval deny)** is a real bug but a 128-bit random approval-id makes practical risk small. Fix same-week but without panic.

**L-02 (normalize dedupe race)** is documented in KNOWN_GAPS as an acknowledged gap. It's a real bug only under concurrent retries on the same raw, which is rare but becomes common if the sync queue ever has delivery-guarantee surprises. A unique index at the DB level closes it permanently.

**F-16 (retention ORDER BY)** — the feature that was shipped as "drain backlog across ticks" doesn't actually drain deterministically. Simple fix; high-ROI because it makes the feature behave as documented.

### Third-tier (this-quarter)

## 2. Functionality

Findings from the eight end-to-end flow traces. Each was returned by an Explore agent and spot-checked against source where the severity warranted it. Tentative severities; Phase 6 triage may adjust.

Locations use file paths relative to `backend/src/contextedge/` unless otherwise noted.

### F-01 — Deduped evidence items skip correlation — **FALSE POSITIVE**

On re-tracing the control flow: the `correlate_evidence.delay(...)` call lives in the Celery task wrapper's post-processing block (`normalize_evidence` at L390+), not inside `_normalize`. The wrapper runs for both new and deduped paths, and the `if attachment_ids / else` branch correctly routes to either attachment extraction (which later enqueues correlate) or direct correlate+baseline enqueue. `register_attachment_artifacts` returns only NEW artifacts, so a deduped item whose artifacts were already registered has empty `attachment_ids` and hits the `else` branch → correlate runs. No finding.

### F-02 — `classify_relevance_task` drops instrumentation — **FIXED**

`workers/extraction_tasks._classify` now passes `tenant_id=tenant_id, db=db` to `run_relevance_classifier`, matching the inline call in `_normalize`. Manual re-classifications will now land in `/admin/cost` and respect the tenant budget gate.

### F-03 / C-04 (merged) — `generate_embedding` call sites miss `tenant_id` / `db` — **FIXED**

`ai/embeddings.py::embed_evidence` and `embed_decision` now accept `tenant_id` + `db` kwargs and forward them. `services/episode_service.py::create_episodes_from_evidence` + `workers/pattern_tasks.py::cluster_episodes` updated to pass the ambient tenant context. Embeddings now land in `/admin/cost` and go through the pre-call budget gate. Two remaining `generate_embedding` call sites in `search/vector_search.py` + `search/hybrid_ranker.py` are request-time helpers sometimes used outside a tenant context; left for a follow-up pass when the caller chain is threaded.

### F-04 — Legal-hold evidence can reach the episode LLM — **FIXED**

Fixed in the same batch as F-23 via a shared helper `services.evidence_filters.exclude_legal_hold`. `workers/extraction_tasks._reconstruct` now filters out `sensitivity_label == "legal_hold"` before building the items list. Regression test in `tests/test_review_legal_hold_fixes.py` asserts the held item is not passed to the extractor.

### F-06 — Silent zero-episode outcomes not distinguished from failures

```
[nice-to-have] services/episode_service.py ::create_episodes_from_evidence
  observation: Empty extractor output (valid JSON, zero episodes) is
    indistinguishable from LLM failure in the current logs — exception
    path logs episode_reconstruction_llm_failed, success path logs
    nothing when the list is empty.
  fix: Add a distinct info log for the zero-result case so ops can tell
    a drift vs an outage.
```

### F-08 — Pattern → playbook is not auto-enqueued

```
[nice-to-have] Playbooks are never generated without manual trigger
  location: services/pattern_service.py::create_pattern_from_episodes
  observation: After a Pattern row is created, nothing enqueues
    generate_playbook_candidate. The only callers are POST
    /playbooks/generate and a manual .delay. Patterns therefore
    accumulate without candidate playbooks unless someone clicks.
  fix: Enqueue generate_playbook_candidate.delay(pattern_id, tenant_id)
    at the end of create_pattern_from_episodes, behind a flag if
    eager-generation is too noisy.
```

### F-09 — Runtime `/explain` cache not invalidated on playbook transitions — **FIXED**

`services.playbook_service.transition_playbook` now accepts an optional `redis` kwarg; when provided, it runs a tenant-scoped `scan_iter("runtime:match:*") + delete` sweep so any cached match for that tenant is dropped on transition. `api/v1/playbooks.transition` passes Redis in from `request.app.state`. Two unit tests in `tests/test_playbook_service.py` confirm (a) same-tenant keys are deleted while other tenants' keys survive, and (b) absent Redis is a no-op (transition still commits). Trade-off: coarse-grained (whole-tenant) rather than per-playbook — acceptable at a 3600s TTL and a reviewer-initiated rare code path.

### F-10 — Playbook FTS search has no access-policy exclusion — **RECLASSIFIED → nice-to-have**

Verified against the `Playbook` ORM model: there is no `access_policy_id` column today — only `approval_policy_id` (governing who can approve transitions) and the implicit tenant_id scope. The evidence paths filter out access-restricted rows because `EvidenceItem` has `access_policy_id`; the playbook paths don't need the same filter because the column it would reference doesn't exist. No current data-leak surface. Retaining as a nice-to-have reminder: if / when playbooks gain `access_policy_id`, `search_playbooks_fts` + the hybrid ranker's playbook retrieval both need the same `notin_()` treatment evidence queries already have.

### F-11 — `decide_approval` mutates `step_run` without tenant check — **FIXED**

Both branches (deny + approve) now guard `step.tenant_id == tenant_id` before mutating the step_run, matching the pattern `modify_approval` already uses. New regression test `test_decide_approval_deny_skips_foreign_tenant_step_run` in `test_p2_execution.py` pins the invariant.

### F-12 — Expired playbooks still executable — **FIXED**

`start_execution` now raises `ExecutionPolicyError` when `playbook.expiry_at` is in the past, directly after the `lifecycle_state == "approved"` check. Test: `test_start_execution_rejects_expired_playbook`.

### F-13 — Shadow approvals are created but never resolved — **FIXED**

Picked option (b) from the original fix suggestion: `start_execution` now creates the approval_request rows (preserves the audit surface — "what would this run have asked approval for?") and **immediately** stamps them as `approved` with a decision_comment `"shadow mode — auto-approved (no human intervention)"`. The run + every approval-gated step_run is then flipped back to `running`, so a shadow run never blocks. Test: `test_shadow_mode_auto_approves_gated_steps`.

Option (a) (skip approval creation entirely) was rejected because it loses the audit value. A reviewer asking "if this playbook had been full_auto, which steps would have asked approval?" gets a correct answer under (b); under (a) the answer is "we don't know — they weren't recorded".

### F-14 — Step-level outputs not tagged in shadow mode

```
[nice-to-have] record_step_completion doesn't mirror the shadow tag
  location: services/execution_service.py::record_step_completion (L315)
  observation: record_tool_invocation tags tool-level outputs with
    `shadow: True`; record_step_completion doesn't mirror this on
    step_run.outputs. Analytics queries against step_run.outputs
    can't separate shadow from real execution.
  fix: Apply the same tagging in record_step_completion.
```

### F-15 — Approval decisions have no row-level lock — **FIXED**

Both `decide_approval` and `modify_approval` now load the `ApprovalRequest` via `db.execute(select(...).with_for_update())` instead of `db.get(...)`. Concurrent calls on the same approval serialise at the DB level — the second one sees `req.status != "pending"` after the first commits and raises `ExecutionPolicyError`. Test mocks in `test_p2_execution.py` and `test_decision_graph.py` were updated to satisfy the new `.execute(...).scalar_one_or_none()` path alongside existing `db.get` mocks.

### F-16 — Retention purge has no `ORDER BY`, so the oldest-first drain doesn't hold — **FIXED**

`purge_archived_evidence` now `order_by(EvidenceItem.updated_at.asc())` before `.limit(limit)`. Oldest rows drain first tick-over-tick.

### F-17 — `soft_purge` leaves PII in `canonical_entity_refs` — **FIXED**

`services.retention_service.purge_archived_evidence` soft-purge branch now also NULLs `canonical_entity_refs` (identity + decision names extracted from the body) and `raw_object_ref` (pointer to the S3 blob). Module docstring updated. Existing `test_purge_soft_purge_scrubs_content_but_keeps_row` extended to assert both new NULLs.

### F-18, F-20, F-21 — Dangling references on hard-delete

```
[important] MinIO blobs, graph_edges, playbook_evidence_links not
            cleaned when hard_delete removes evidence
  location: services/retention_service.py (hard_delete), models/pattern
    .py::GraphEdge, models/playbook.py::PlaybookEvidenceLink
  observation: hard_delete removes the EvidenceItem row, FK-cascades to
    attachment_artifacts, correlation_edges (ORM), contradiction_scan_
    state. But:
    (a) RawEvidenceObject blob in MinIO is never deleted; the row in
        raw_evidence_objects also stays (raw_object_ref is a plain
        UUID, not a FK).
    (b) graph_edges rows referencing the deleted evidence id as
        source_node_id/target_node_id stay as orphan references. The
        docstring says a "graph-compact job" cleans them up — no such
        job is scheduled.
    (c) playbook_evidence_links.evidence_id is a plain UUID with no
        FK, so links stay even though the evidence is gone.
  fix: Ship a graph-compact + blob-reaper Celery task (daily Beat),
    and add a proper ForeignKey to playbook_evidence_links.evidence_id
    with ON DELETE SET NULL or CASCADE (pick one and document). Note
    L-01 — FK additions for older deploys require ALTER migrations,
    not just ORM changes.
```

### F-19 (merged) — `PlaybookEvidenceLink.evidence_id` has no FK

Covered in F-18 block above. Flag for the consolidated fix.

### F-22 — Contradiction scan's HNSW top-K applies domain filter after LIMIT

```
[important] Domain-scoped tenants don't benefit from HNSW pre-filter
  location: services/contradiction_service.py::_top_k_kb_candidates
    (≈ L195-210)
  observation: The query does `.order_by(embedding.cosine_distance(q))
    .limit(k)` and THEN applies the domain_id predicate. That means
    the K candidates are chosen globally across the tenant and shrunk
    post-fact by domain, so a 5-domain tenant with domain-scoped
    retrieval misses candidates that the HNSW could have returned had
    the filter been in the WHERE.
  fix: Move the domain filter (and any sensitivity_label filter per
    F-23) into the initial WHERE before the ORDER BY. Indexed predicates
    will cooperate with HNSW via PostgreSQL's planner; the current
    order defeats 70%+ of the index benefit for scoped queries.
```

### F-23 — Contradiction scan has no legal-hold exclusion — **FIXED**

`services.contradiction_service._top_k_kb_candidates` now calls the shared `exclude_legal_hold()` helper and includes the predicate in the WHERE. As a bonus, the same edit fixed **F-22** (the domain filter was being applied after `ORDER BY / LIMIT`) by collapsing all predicates into a single `.where(*predicates)` call before the ORDER BY — HNSW now cooperates with the filter instead of being defeated by it. Regression test in `tests/test_review_legal_hold_fixes.py` asserts the helper is still referenced in the function source.

### F-24 — No uniqueness constraint on `contradictions(tenant_id, source_a, source_b)` — **FIXED**

Migration `0026_dedup_uniqueness` adds `uq_contradictions_tenant_source_pair` via `CREATE UNIQUE INDEX CONCURRENTLY`. `_get_or_create_contradiction` now catches `IntegrityError` on the `flush`, rolls back, re-SELECTs the winning row, and refreshes its mutable fields — matches the "existing-row" branch result for the loser. Regression test in `test_review_dedup_uniqueness.py`.

### F-25, F-26, F-27, F-28 — Contradiction scan lesser issues

```
[nice-to-have] F-25 Token-overlap gate passes overly-short matches
  location: services/contradiction_service.py (overlap helper)
  observation: `overlap >= 2 OR (overlap == 1 AND min(len) <= 4)` lets
    a single-word match on a 1-token KB snippet through (e.g. "MFA"
    matching "must disable MFA"). Fires LLM calls for noise.
  fix: Tighten the second branch to min <= 3 or drop it entirely.

[nice-to-have] F-26 Budget-exhausted scans don't record all skipped pairs
  observation: On budget exhaustion the current pair records
    result="skipped_budget" but the inner loop continues incrementing
    the counter without writing further rows. Queue depth via
    `COUNT(*) WHERE result='skipped_budget'` undercounts.
  fix: `break` out of all loops once budget_exhausted = True, or
    persist every remaining pair at row-level as skipped_budget.

[nice-to-have] F-27 Contradiction notifications fire unbatched
  observation: Each newly-created Contradiction synchronously calls
    notification_service.send_notification. A scan that finds 50
    contradictions sends 50 notifications during the scan's own
    transaction.
  fix: Collect notifications and send a single batched one after the
    flush, or enqueue a lightweight notification-dispatch task.

[nice-to-have] F-28 Rescan cursor compares against a non-existent column
  location: services/contradiction_service.py::_needs_rescan
  observation: The cursor comparison falls back to evidence.ingested_at
    because EvidenceItem has no updated_at column, so "re-ingested
    evidence" is never re-scanned even though the docstring promises
    it.
  fix: Add an updated_at column to evidence_items (or reuse one of
    the timestamp mixins). Note that this migration also helps F-16.
```

### F-29 — Budget race window within the 60s usage cache — **FIXED (partial)**

Picked option (a) — per-tenant `asyncio.Lock` in `tenant_budget_service`. `check_budget` now serialises concurrent callers on the same tenant inside one worker process, so two calls can't both read the same stale cache and both proceed. Cross-worker races (multiple gunicorn replicas or Celery workers) are NOT covered — for that, we'd need a Redis-backed counter with `INCRBY` + atomic compare-against-limit. Documented in the module docstring as the upgrade path. The 15 existing `test_p1_tenant_budget.py` tests still pass (the lock is transparent when there's no contention).

### F-30 — Budget cache not invalidated on tenant delete

```
[nice-to-have] Stale cache after tenant CASCADE delete
  location: services/tenant_budget_service.py::invalidate_cache
  observation: invalidate_cache is called on upsert_budget. There is
    no hook on TenantLLMBudget row deletion (which CASCADEs from
    tenant delete). If a tenant is deleted out from under running
    workers, stale cache entries keyed by the old tenant_id persist
    until TTL expiry.
  fix: SQLAlchemy @event.listens_for(TenantLLMBudget, "after_delete")
    calling invalidate_cache(target.tenant_id), or document that
    tenant deletion is a heavy admin operation that requires a
    worker restart.
```

### C-01 — 15 models carry `tenant_id` without `TenantScopedMixin`

```
[nice-to-have] Tenant-scoping via mixin is inconsistent
  location: backend/src/contextedge/models/{events,pattern,execution,tenant,evaluation,evidence}.py
  axis:     consistency
  observation: Only ~20 of the 44 models inherit TenantScopedMixin; 15 others

### C-02 — 11 endpoints return raw `dict` instead of `response_model=`

```
[nice-to-have] Response schema declarations are missing on 11 endpoints
  location: api/v1/{sources,threads,episodes,patterns,evidence,runtime,correlations,decisions,graph}.py
  axis:     consistency
  observation: 11 routes skip `response_model=` and return a raw dict. This
               means OpenAPI docs don't describe their shape, frontend types
               are hand-written against implementation rather than schema,
               and a shape change won't fail at test time.
  evidence: Appendix A.1. Examples: POST /sources/{id}/backfill,
            POST /patterns/cluster, GET /decisions/effectiveness,
            PATCH /evidence/{id}/relevance, POST /runtime/feedback, all
            three GET /graph/*.
  fix: For each, either add a typed response model, or if the payload is
       genuinely free-form, use a trivial `{"status": ..., "task_id": ...}`
       model called TaskDispatchResponse and reuse it.
```

### C-06 — `response_model=` coverage is very thin

```
[nice-to-have] Only 5 of 22 routers declare a response_model on any route
  location: api/v1/*.py
  axis:     consistency
  observation: Grep for `response_model=` returns 10 total occurrences
    across 5 files (decisions, playbooks, execution, evidence, sessions).
    The other 17 routers — including admin_cost, sources, evidence writes,
    runtime, graph, review_queue — return either plain Pydantic instances
    or dicts without declaring the OpenAPI shape. Effect: Swagger / ReDoc

## 4. Logic

Findings from Phase 4 invariant + edge-case review. A few jumped out of the Phase 1 inventory already and are captured here pending verification.

### L-01 — `correlation_edges` CASCADE is ORM-only; deployments that ran `0001_initial` before 2026-04-20 don't have it

```
[important] ORM-DDL drift: CorrelationEdge FK CASCADE was added to the
            model post-0001 but no migration ALTERs existing tables
  location: backend/src/contextedge/models/episode.py:80-81
            (CorrelationEdge.source_evidence_id, .target_evidence_id)
  axis:     logic
  observation: The ORM model declares ondelete="CASCADE" on both FKs,
               so fresh databases that run `alembic upgrade 0001` *after*
               commit 45ad8791 (2026-04-20) get CASCADE via
               `Base.metadata.create_all()`. But deployments that ran
               0001_initial BEFORE that commit — say, a pilot env that
               migrated in March — have the old `NO ACTION` (RESTRICT)
               constraint. No subsequent migration adds the CASCADE via
               ALTER TABLE. The retention service docstring now claims
               correlation_edges cascade, and purge_archived_evidence
               (mode="hard_delete") relies on it. On an older DB this
               quietly breaks: the DELETE on evidence_items raises a
               ForeignKeyViolation when correlation edges reference it,
               and the whole purge batch aborts.
  evidence: git blame episode.py:80-81 → commit 45ad8791 (2026-04-20);
            grep for "correlation_edges" in alembic/versions/ returns
            zero matches (no ALTER). Confirmed ORM code has CASCADE;
            confirmed no migration propagates it.
  fix: Add a new migration that runs
       `ALTER TABLE correlation_edges DROP CONSTRAINT
         correlation_edges_source_evidence_id_fkey,
         ADD CONSTRAINT ... ON DELETE CASCADE`
       for both FKs, idempotent via information_schema guard. This is
       the same pattern you'll need for any FK tightening added
       post-0001 — consider auditing every model FK for drift in a
       single pass.
```

Severity is **important** not **critical** because (a) fresh installs are correct, (b) the bug is triggered only when a customer actually runs hard-delete purge on correlated evidence, which most haven't yet, and (c) the failure mode is a loud exception, not silent data loss. Verify by diffing a production `\d+ correlation_edges` against the ORM declaration — that's the ground truth.

This is also a **class of findings** — the broader problem is that `0001_initial` using `create_all()` means any ORM tightening after 0001 ships (FK constraints, nullability, defaults) silently diverges on older DBs. A complete audit would grep every model for FK `ondelete=` / `nullable=False` / etc. added post-`056eb846` and confirm each has a corresponding ALTER migration.

### L-02 — Normalize worker has a check-then-insert dedupe race — **FIXED**

Migration `0026_dedup_uniqueness` adds a partial unique index `uq_evidence_items_tenant_content_hash` on `(tenant_id, content_hash) WHERE content_hash IS NOT NULL` — partial because pre-hash-populate legacy rows would otherwise collide on NULL. `_normalize` now catches `IntegrityError` on the new-item flush, rolls back, re-fetches the winning row, and returns a `raced=True` dedup result without re-running the enrichment pipeline (the winning worker already did it — re-running would be wasted LLM spend). Regression test in `test_review_dedup_uniqueness.py`. The README's Known Constraints acknowledgement should be updated — noted as a follow-up doc pass.

## Appendix B — What was not reviewed

Honest list of the gaps in this review. Findings not here don't exist on paper; findings here may exist and weren't checked.

- **The one-file services that I didn't re-read** — `memory_service`, `runtime_service`, `source_service`, `sync_worker_service` were covered at interface level via agent inventory but not line-by-line. High-complexity surface; a targeted re-read would probably turn up a handful more findings.
